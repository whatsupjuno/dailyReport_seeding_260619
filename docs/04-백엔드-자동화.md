# 04 · 백엔드 자동화 (이메일 / 스케줄 / 링크 토큰)

> 제품: **Seeding (What The Hell Are You Doing?)** — 팀원의 일일 업무 보고를 받고 검수하는 사내 웹 시스템
> 스택: Next.js(App Router) + Node.js + PostgreSQL · cafe24 linux 호스팅 · 메일 **NCP Outbound Mailer** · 타임존 **KST(Asia/Seoul)** · 영업일=평일
> 근거: `_design_decoded.html`(로그인 배너 `loginBanner` "로그인하면 6월 18일 업무 보고서로 바로 이동합니다", OTP 4자리 `otpDigits`/`인증번호`, `writeMode` 7모드, `stepperNodes` 시각맵 `{plan:'08:30', morning:'11:50', afternoon:'17:50', night:'21:30'}`, 야간 종료 예상시각·`night_expected_end_at`), `02-데이터모델.md`(`notifications`/`auth_otps`/`daily_reports`/`report_links`/`report_sections`/`sessions`).

이 문서는 **화면이 아니라 백엔드 자동화**(이메일 발송·스케줄·링크 토큰·리마인더·반려 알림)를 다룬다. 모든 enum/컬럼/테이블 이름은 `02-데이터모델.md`의 정의를 그대로 사용한다. 디자인에 없는 합리적 보강은 `[보강]`, 불명확 지점은 `[확인필요]`로 표기한다.

전제(공통):
- **저장은 `timestamptz`(UTC), 판정은 앱에서 `Asia/Seoul`로 변환**한다. "오늘 보고서"는 `daily_reports.report_date date`(KST 영업일)로 식별한다.
- 모든 발송은 `notifications` 1행으로 로깅하며, **멱등키 `dedup_key`(UNIQUE)** 로 중복발송을 차단한다.
- 발송 주체는 단일 **스케줄러 워커(스윕 잡)** 이며, 화면 트래픽과 독립적으로 동작한다(§5.6).

## 1) 발송 스케줄 표 (평일)

평일(영업일) 기준 고정 시각 3건 + 야간 동적 1건 + 리마인더(파생). 각 발송은 대상 사용자의 **당일 `daily_reports`(없으면 생성)** 를 향하고, 메일에는 **링크 a**(`report_links.token`, §2)와 필요 시 **로그인 OTP**(`auth_otps`, §2.4)가 동봉된다.

| 발송 시각(KST) | 트리거 | 대상(수신자) | 메일 종류 `notification_kind` | 생성/갱신되는 보고서·시간대 | 비고 |
|---|---|---|---|---|---|
| **08:30** | 평일 고정 스케줄(영업일만) | 활성 사용자 전원(휴가 예정자 제외) | `plan_link` | 당일 `daily_reports` upsert(없으면 생성, `status=not_written`) + `report_sections(kind='plan')` 보장. writeMode 진입 = `morningPlan` | 디자인 stepper `plan:'08:30'`. 오늘 계획 작성 유도 |
| **11:50** | 평일 고정 스케줄 | 미완(미마감)·미휴가 사용자 | `morning_close_link` | `report_sections(kind='morning')` 보장 + 오후 계획 블록. writeMode = `morningClose`(오전 마감 + 오후 계획) | stepper `morning:'11:50'` |
| **17:50** | 평일 고정 스케줄 | 미완·미휴가 사용자 | `afternoon_close_link` | `report_sections(kind='afternoon')` 보장 + 야간 분기 토글. writeMode = `afternoonClose`(오후 마감 + 야간 분기) | stepper `afternoon:'17:50'` |
| **야간 종료 예상시각 − 10분** | `daily_reports.night_branch=true` & `night_expected_end_at IS NOT NULL`인 보고서, 종료 10분 전 도달 시 1회 | 해당 야간 사용자 | `night_link` | `report_sections(kind='night')` 재진입. writeMode = `nightClose` | stepper 예시 `night:'21:30'` → 21:20 발송. **동적**(고정 시각 아님) |
| **발송 후 30분~ (5분 간격)** | 직전 안내 메일 발송 후 30분 경과 시점에 해당 시간대 **미작성/미제출**이면 시작, 이후 5분 단위 | 미작성 사용자 | `reminder` | 보고서·시간대 변경 없음(알림만) | §3 상태머신. 완료/제출 시 중단 |
| **반려 즉시(이벤트)** | 그룹장 `reviews(action='reject')` 커밋 | 보고서 작성자(`daily_reports.owner_id`) | `reject_notice` | 변경 없음(지목 시간대 `rework`는 검수 트랜잭션에서 처리) | §4 |
| **승인 즉시(이벤트)** `[확인필요]` `[v1 deferred]` | 그룹장 `reviews(action='approve')` 커밋 | 작성자 | (해당 enum 없음 → 발송 안 함) | 변경 없음 | §7. 데이터모델 `notification_kind`에 승인 종류 미정의(`approve_notice` 없음)이고 01-기능명세·03-API도 승인 메일을 정의하지 않음 → **v1에서는 승인 메일을 발송하지 않는다**. 발송이 필요하면 enum 추가 후 결정 |

> **시간대 매핑 근거(디자인)**: `stepperNodes()`의 `times = { plan:'08:30', morning:'11:50', afternoon:'17:50', night:'21:30' }`, 섹션 range 라벨 `오전 08:30~11:50 / 오후 11:50~17:50 / 야간 17:50~21:30`. `writeMode` 7모드(`morningPlan→morningClose→afternoonClose→nightClose→view`, 그리고 `vacation`/`rejected`)와 일대일 대응.

### 1.1 발송 시 보고서 보장(upsert) 의사코드 `[보강]`

각 스케줄 발송은 **대상 사용자에게 당일 보고서·해당 시간대 섹션을 보장**한 뒤 링크를 동봉한다.

```text
ensureReport(user, reportDate):
  report = SELECT … FROM daily_reports WHERE owner_id=user.id AND report_date=reportDate
  if not report:
     report = INSERT daily_reports(owner_id, group_id=user.group_id 스냅샷,
                                   report_date, status='not_written')
  link = ensureReportLink(report)        // §2.2 (보고서당 1개)
  return report, link

ensureSection(report, kind):
  INSERT report_sections(report_id, kind, status='not_written', is_locked=false)
  ON CONFLICT (report_id, kind) DO NOTHING   // uq_section_report_kind
```

### 1.2 대상 산정 규칙

- **공통 제외**: `users.status='inactive'`, `users.deleted_at IS NOT NULL`, `role='admin'`(작성 의무 없음 `[확인필요]`), 당일 휴가자(§5.5).
- **11:50 / 17:50 / 리마인더**: 직전 단계 미완 사용자만(이미 해당 시간대 `report_sections.is_locked=true`(마감완료)거나 `daily_reports.status IN ('submitted','pending_review','resubmitted','approved','vacation')`이면 제외). 단순 편집 중(`section_status='writing'`)은 미완으로 보아 제외하지 않는다(§3.1과 동일 판정).
- 그룹장도 **직원처럼 작성**하므로 발송 대상에 포함된다(도메인 계약).

## 2) 링크 a 토큰 모델 (일일 단위 누적)

### 2.1 모델 개요

링크 a = **일일 단위 누적 토큰**. 하루 동안 보낸 모든 안내 메일(계획/오전/오후/야간)이 **같은 토큰**을 사용해 **같은 `daily_reports` 행을 반복 갱신**(append/edit)한다. 디자인의 "메일 링크(배너)" 진입(`loginBanner`)과 "로그인하면 6월 18일 업무 보고서로 바로 이동합니다"가 이 모델의 표현이다.

- 저장: `report_links(report_id, token uuid, expires_at, revoked_at)`, `UNIQUE(report_id)` → **보고서(=하루)당 토큰 1개**, `UNIQUE(token)`.
- URL 형태 `[보강]`: `{APP_BASE_URL}/r/{token}` (예: `https://seeding.example.com/r/3f2c…`). 메일 CTA 버튼이 이 링크를 가리킨다.

### 2.2 생성 (idempotent)

```text
ensureReportLink(report):
  link = SELECT * FROM report_links WHERE report_id = report.id
  if link and link.revoked_at is null and link.expires_at > now():
     return link                              // 재사용(누적)
  // 없거나 만료/폐기 → 생성(또는 갱신)
  INSERT report_links(report_id, token=gen_random_uuid(),
                      expires_at = KST 영업일 종료 경계)   // §2.5
  ON CONFLICT (report_id) DO UPDATE
     SET token = EXCLUDED.token, expires_at = EXCLUDED.expires_at, revoked_at = NULL
  RETURNING *
```

> 같은 날 두 번째·세 번째 메일(오전/오후/야간)은 새 토큰을 만들지 않고 **기존 토큰을 재사용** → "하루 동안 동일 링크로 누적".

### 2.3 검증 (링크 클릭 시)

```text
resolveLink(token):
  link = SELECT * FROM report_links WHERE token = $token
  if not link:                 → 404 "유효하지 않은 링크"
  if link.revoked_at:          → 410 "만료된 링크"
  if link.expires_at <= now(): → 410 "오늘 보고서 링크가 만료되었습니다(자정 경과)"
  report = daily_reports[link.report_id]
  user   = users[report.owner_id]
  return { report, user }
```

링크는 **세션을 자동 부여하지 않는다**(보안). 클릭 시 흐름은 §2.4 참조.

### 2.4 OTP와의 관계 (인증)

디자인 로그인 화면은 **아이디 + 4자리 인증번호(OTP)** 를 요구한다. 링크 a는 "어떤 보고서로 갈지"를 가리키는 **딥링크**이고, **로그인 자체는 OTP로** 한다.

- 안내 메일에는 **링크 a + 그 사람용 OTP(4자리)** 가 함께 동봉된다(디자인 "인증번호는 발송된 보고 안내 메일에서 확인할 수 있습니다").
- `auth_otps`: 발송 시 `purpose='login'`, `report_date`(해당 보고서 날짜, 당일 이동용), `expires_at`, `code_hash`(평문 저장 금지). `notification_kind`는 메일 본문에 OTP를 실어 보내는 경우 `login_otp` 또는 각 링크 메일에 포함 `[확인필요]`.
- 흐름:
  1. 사용자가 메일의 **링크 a 클릭** → `/r/{token}` → `resolveLink`로 보고서/사용자 식별 → 로그인 화면을 **아이디 프리필 + 배너("…보고서로 바로 이동")** 로 렌더(디자인 `loginBanner=true`).
  2. 사용자가 **메일의 4자리 OTP 입력** → `auth_otps` 검증(아래) → `sessions` 발급 → **해당 `report_date` 보고서로 바로 이동**(로그인 후 당일 보고서). 디자인 데모: `kim.minji`/`7391`, 오류 재현 `0000`.

```text
verifyOtp(loginId, code, token?):
  user = users[login_id = loginId, deleted_at IS NULL, status='active']
  otp  = SELECT * FROM auth_otps
         WHERE user_id=user.id AND consumed_at IS NULL AND expires_at > now()
         ORDER BY created_at DESC LIMIT 1
  if not otp or otp.attempt_count >= MAX_ATTEMPTS(=5 [보강]):
      → 423 "잠시 후 다시 시도해 주세요"
  if hash(code) != otp.code_hash:
      UPDATE auth_otps SET attempt_count = attempt_count + 1
      → 401 "인증번호가 일치하지 않습니다"  (디자인 카피와 동일)
  UPDATE auth_otps SET consumed_at = now()
  session = INSERT sessions(user_id, token_hash, expires_at)
  redirectReportDate = token ? resolveLink(token).report.report_date
                             : otp.report_date ?? todayKST()
  → set-cookie(session) + redirect(/reports/{redirectReportDate})
```

> **링크와 OTP 결합**: 토큰만으로는 로그인되지 않으므로(메일 유출 방어), 토큰 + 본인 OTP가 모두 필요하다. 토큰은 "목적지", OTP는 "신원". `[보강]`

### 2.5 만료 (KST 영업일 경계)

- `report_links.expires_at` = **해당 `report_date`의 KST 23:59:59**(자정 경과 시 만료) `[보강]`. 단, 야간(`night_expected_end_at`)이 자정을 넘는 경우 `expires_at = max(자정, night_expected_end_at + 버퍼)` `[확인필요]`.
- `auth_otps.expires_at` = 발급 후 **단기**(예: **5분** `[보강]`, 03-API §1.1 `expires_in_sec: 300`·§3.1과 동일값으로 통일). 만료 시 로그인 화면에서 "인증번호 재발송" 필요 `[확인필요: 재발송 UI 디자인에 없음]`.
  - 트레이드오프 `[확인필요]`: 안내 메일에 OTP를 동봉(하루 단위 링크와 함께)하는 모델에서는 메일 수신 후 작성 시점까지 OTP가 유효해야 하므로 5분이 과도하게 짧을 수 있다. 이 경우 **링크 a 클릭 시점에 OTP를 새로 발급**(`auth_otps` 재발급)하거나, 보안 정책상 OTP 만료를 늘리는 방안을 택한다. v1은 03-API와 맞춘 5분을 정본으로 한다.
- 폐기: 보고서가 다음 날로 넘어가면 자연 만료. 보안 사고 시 `revoked_at` 수동 세팅.

## 3) 리마인더 상태머신

**규칙(도메인 계약)**: 직전 안내 메일 발송 후 **30분 내 미작성**이면 **5분 단위 재알림**, **작성 완료/제출 시 중단**.

### 3.1 상태 정의

각 (사용자, 영업일, 시간대 단계) 단위로 리마인더 트랙을 운용한다.

```
            안내메일 sent
                │
                ▼
        ┌──────────────┐   30분 경과 & 여전히 미작성
        │  WAITING     │ ───────────────────────────► REMIND(seq=1)
        │ (관망 30분)   │
        └──────────────┘   작성/제출/마감/휴가  →  DONE(중단)
                                   ▲
        ┌──────────────┐  +5분 & 미작성          │
        │ REMIND(seq=n)│ ──────────────► REMIND(seq=n+1)
        └──────────────┘
            │  작성/제출/마감/휴가
            ▼
          DONE (중단, 더 이상 발송 안 함)
```

- **WAITING**: 안내 메일(`plan_link`/`morning_close_link`/`afternoon_close_link`/`night_link`) `sent` 시각 + 30분까지 대기.
- **REMIND(seq=n)**: `notifications(kind='reminder', reminder_seq=n)`. seq=1은 발송+30분, 이후 +5분마다 seq 증가.
- **DONE(중단 조건)**: 해당 시간대가 **마감/제출/승인/휴가** 상태가 되면 즉시 중단.
  - 판정: 다음 중 하나면 중단 — `report_sections.is_locked=true`(마감완료) 또는 `report_sections.status='closed'`, `daily_reports.status IN ('submitted','pending_review','resubmitted','approved','vacation')`, 또는 그날 휴가 등록.
  - **주의**: 단순 편집 중(`section_status='writing'`, 작성중)은 **미완으로 보아 리마인더를 계속한다**. `writing`은 "편집 중(미마감)" 상태이지 완료가 아니므로 중단 조건에서 제외(03-API §1.11 "미작성(`status in not_written/writing` 대상)" 문구와 일치).
- **상한**: `reminder_seq` 최대치(예: 다음 단계 발송 시각 도달 또는 seq≤12 `[보강]`)에서 종료해 무한 발송 방지.

### 3.2 다음 리마인더 due 계산

```text
nextReminderDueAt(track):
  if track.reminder_seq is null:           # 아직 리마인더 0회
      return track.base_sent_at + 30분
  else:
      return track.last_reminder_at + 5분
```

`base_sent_at` = 직전 안내 메일의 `notifications.sent_at`(해당 단계). `[보강]`

### 3.3 멱등성·중복발송 방지

- **멱등키**: `dedup_key = '{kind}|{user_id}|{report_date}|{section_kind}|{reminder_seq}'`.
  - 안내: `plan_link|42|2026-06-18|plan` (seq 없음)
  - 리마인더: `reminder|42|2026-06-18|morning|3`
  - `section_kind`은 `02-데이터모델.md` §2.4의 실존 enum 값(`plan`/`morning`/`afternoon`/`night`)을 그대로 쓴다. 안내·리마인더는 시간대 구분이 필요하므로 데이터모델 §3.18·03-API §1.11의 정본 포맷(`kind|user_id|report_date|reminder_seq`)에 `section_kind` 세그먼트를 추가한 형태이며, **세 문서가 동일하게** 이 포맷을 사용한다. `dedup_key`는 `notifications`의 자유 텍스트 컬럼이므로 별도 `stage`/`section_kind` 컬럼은 필요 없다(`notifications`에는 `kind/user_id/report_id/report_date/reminder_seq` 컬럼만 존재).
- `notifications.UNIQUE(dedup_key)`(제약명 `uq_notif_dedup`) → 동일 키 INSERT 충돌 시 `status='skipped'`로 처리하거나 무시(멱등). 스윕 잡이 한 틱에 두 번 돌아도 같은 메일이 두 번 나가지 않는다.
- **트랜잭션 경계**: "due 행 선점 → NCP 전송 → `sent`/`failed` 기록"을 한 트랜잭션 단위로 묶되, 외부 호출(NCP)은 트랜잭션 밖에서 하고 결과만 UPDATE(아래 §5.6 outbox 패턴).

### 3.4 재시도

- NCP 호출 실패 시 `notifications.status='failed'`, `error` 기록. **백오프 재시도**(예: 즉시→1분→5분, 최대 3회 `[보강]`). 재시도는 **같은 `dedup_key` 행을 갱신**(새 행 생성 금지)하여 중복 방지.
- 영구 실패(3회 초과)는 `failed` 고정 + 운영 알림 `[확인필요]`.
- 리마인더는 재시도 중 작성 완료되면 다음 틱에서 **중단 조건**을 먼저 평가 → 불필요한 재시도 자동 소멸.

## 4) 반려 알림 (재작성 안내 메일)

### 4.1 트리거

그룹장이 반려 모달에서 제출 → `reviews(action='reject', comment 필수)` + `reject_targets(scope ∈ all/morning/afternoon/night)` + `review_events(event_type='rejected')` 커밋이 **성공한 직후**, 동일 트랜잭션 커밋 후 **outbox**로 `notifications(kind='reject_notice')` enqueue.

- 멱등키: `reject_notice|{owner_id}|{report_date}|{round}`(검수 회차당 1통). `round`는 `reviews.round`(검수 회차) 값으로, 재반려 시 회차가 달라져 새 안내가 1통 나간다. `notifications`에는 `review_id` 컬럼이 없으므로(데이터모델 §3.18) 멱등키에 `review_id`를 쓰지 않고 회차(`round`)로 구분한다. `[보강]`
- 수신자: `daily_reports.owner_id`.
- 부수효과(데이터): 지목된 시간대 section을 `is_locked=false`, `section_status='rework'`로 열고 나머지는 잠금 유지(= rejected 모드, `02-데이터모델.md` §5.3). **이 부수효과는 검수 트랜잭션에서**, 메일은 그 후 발송.

### 4.2 메일 내용(핵심 변수)

- 제목: `[Seeding] {report_date} 보고서가 반려되었습니다 — 재작성 요청`
- 본문 변수: 작성자명, `report_date`, **반려 사유 코멘트**(`reviews.comment`, 필수), **지목 시간대**(`reject_targets.scope` → "오후/야간" 등), 선택된 템플릿 라벨(`reviews.template`: 일정 누락/근거 불충분/완결 처리 오류/커뮤니케이션 기록 누락/내용 구체화 필요), **재작성 링크 a**(`{APP_BASE_URL}/r/{token}`) + OTP(필요 시).
- CTA: "지목된 시간대 재작성하기" → 클릭 시 §2.4 흐름으로 로그인 후 해당 보고서(rejected 모드)로 진입. 디자인 직원 읽기 화면의 "재작성 링크" 영역과 대응.

## 5) NCP Outbound Mailer 연동 & 스케줄러 구현

### 5.1 환경 변수(이미 `.env`에 존재)

```
MAIL_TRANSPORT=log|ncp          # log=실발송 없음(dev/test 기본), ncp=실발송
MAIL_FROM_ADDRESS=no-reply@…    # 발신 주소
MAIL_FROM_NAME=Seeding          # 발신자 표시명
NCP_ACCESS_KEY_ID=…             # IAM 키(HMAC 서명용)
NCP_SECRET_KEY=…
NCP_MAILER_DOMAIN_VERIFICATION=…# 발신 도메인 소유 확인(DNS TXT)
APP_BASE_URL=…                  # 링크 a 절대경로 생성에 사용
TZ=Asia/Seoul
```

> `MAIL_TRANSPORT=log`는 실제 전송 없이 `notifications`에 기록만 → 개발/테스트에서 발송 흐름 검증. 운영은 `ncp`.

### 5.2 NCP 요청 형태 (Outbound Mailer · 메일 발송 API)

- **엔드포인트**: `POST https://mail.apigw.ntruss.com/api/v1/mails` `[확인필요: API 버전/리전]`
- **인증 헤더**(HMAC-SHA256 서명):
  - `x-ncp-apigw-timestamp: {epochMillis}`
  - `x-ncp-iam-access-key: {NCP_ACCESS_KEY_ID}`
  - `x-ncp-apigw-signature-v2: {base64(HMAC-SHA256(secret, method + " " + url + "\n" + timestamp + "\n" + accessKey))}`
  - `Content-Type: application/json`
- **요청 바디(스케치)**:

```json
{
  "senderAddress": "{MAIL_FROM_ADDRESS}",
  "senderName": "{MAIL_FROM_NAME}",
  "title": "{제목 — §6 템플릿}",
  "body": "{HTML 본문 — 템플릿 변수 치환}",
  "recipients": [
    { "address": "{to_email}", "name": "{user.name}", "type": "R",
      "parameters": { "userName": "…", "reportDate": "…", "ctaUrl": "…", "otp": "…" } }
  ],
  "individual": true,
  "advertising": false
}
```

- **응답**: `requestId`/`mailId` → `notifications.ncp_message_id`에 저장.
- **템플릿 변수**: 위 `parameters`(개인화 치환). 공통 변수 — `userName`, `reportDate`(KST), `ctaUrl`(링크 a 절대경로), `otp`(4자리, 필요 시), `sectionLabel`(오전/오후/야간), `deadline`(11:50/17:50/종료시각), `rejectReason`/`rejectScope`(반려), `reviewerName`(반려/승인).

### 5.3 발신자·도메인

- 발신: `MAIL_FROM_ADDRESS`(`MAIL_FROM_NAME` 표시명). 발신 도메인은 NCP에서 **DNS TXT(`mailer.domain.verification`)** 로 사전 검증(`NCP_MAILER_DOMAIN_VERIFICATION`). SPF/DKIM 설정 권장 `[보강]`.

### 5.4 실패 처리

- HTTP 4xx/5xx 또는 타임아웃 → `notifications.status='failed'`, `error`에 응답코드/메시지 기록 → §3.4 백오프 재시도. 4xx(잘못된 수신지 등)는 재시도 무의미 → 즉시 `failed` 고정 `[보강]`.
- 부분 실패(다수 수신자) 방지를 위해 **수신자 1명당 1요청(individual)** 으로 발송 → 멱등키 단위와 1:1.

### 5.5 KST · 영업일 · 휴가자 처리

- **KST**: 컨테이너 `TZ=Asia/Seoul`. 단, 스케줄 판정은 환경에 의존하지 않도록 코드에서 명시적으로 `Asia/Seoul` 변환(예: `Intl.DateTimeFormat('en-CA',{timeZone:'Asia/Seoul'})`) `[보강]`.
- **영업일(평일)**: 토/일 발송 안 함. **공휴일은 `[확인필요]`** — 디자인/도메인에 공휴일 데이터 없음. 보강안: `business_holidays(holiday_date date)` 마스터 추가하여 제외 `[보강]`. 미정 시 v1은 토/일만 제외.
- **휴가자 제외**: 발송 시각에 대상 사용자의 당일 보고서가 `daily_reports.status='vacation'`(또는 `vacations` 1건)이면 모든 안내·리마인더 발송 제외. 휴가는 **사전 등록 가능**해야 휴가 당일 08:30 발송을 막을 수 있음 → 휴가 사전 등록 흐름 `[확인필요]`.

### 5.6 크론 / 스케줄러 구현 방식 (cafe24 linux)

cafe24 공유 호스팅 특성상 **OS `cron` + Next 라우트 호출**을 1순위로, **상주 Node 스케줄러**를 대안으로 둔다. `package.json`에 스케줄러 의존성이 없으므로(추가 라이브러리 불필요) **DB 큐 + 스윕(틱) 잡** 패턴을 채택한다. `[보강]`

**권장(1순위) — OS cron → 보호된 스윕 엔드포인트**:

```cron
# crontab (KST 서버 기준)  ── 매 분 스윕(due 발송 일괄 처리)
* * * * *  curl -fsS -H "X-Cron-Secret: $CRON_SECRET" https://seeding.example.com/api/cron/sweep >/dev/null 2>&1
```

- `POST /api/cron/sweep` (헤더 `X-Cron-Secret` 검증, 외부 호출 차단):
  1. **due 발송 산정**: 08:30/11:50/17:50 정시 도달, 야간 종료−10분 도달, 리마인더 due(§3.2) 행을 한 번에 계산.
  2. **outbox enqueue**: 각 발송을 `notifications`에 `dedup_key`로 INSERT(`ON CONFLICT DO NOTHING`) → 멱등 보장.
  3. **flush**: `status='queued'` 행을 선점(`FOR UPDATE SKIP LOCKED`)하여 NCP 전송 → `sent`/`failed` UPDATE.
- 매 분 실행이라도 멱등키가 같은 메일의 재발송을 막으므로 **중복 없음**. 정시(08:30 등)는 "그 분에 처음 본 due"만 enqueue.

**대안(2순위) — 상주 Node 워커**: `next start`와 별도 프로세스(또는 `instrumentation.ts`에서 단일 `setInterval(…, 60_000)` 부트스트랩)로 동일 스윕 로직 실행. cafe24에서 상주 프로세스/PM2가 가능할 때만 `[확인필요: 호스팅 플랜의 상주 프로세스 허용 여부]`.

**왜 스윕(틱) 패턴인가**: ① 멱등키로 중복발송 원천 차단, ② 워커가 한동안 죽어도 복구 후 누락분을 따라잡음(catch-up), ③ 야간(동적 시각)·리마인더(5분 간격)를 cron 표현식 없이 DB 조건으로 통일 처리.
