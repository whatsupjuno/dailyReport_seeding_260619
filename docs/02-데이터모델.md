# 02 · 데이터 모델 (PostgreSQL)

> 제품: **Seeding (What The Hell Are You Doing?)** — 팀원의 일일 업무 보고를 받고 검수하는 사내 웹 시스템
> 스택: Next.js(App Router) + Node.js + PostgreSQL · cafe24 linux 호스팅 · 메일 NCP Outbound Mailer · 타임존 **KST(Asia/Seoul)** · 영업일=평일
> 근거: `_design_decoded.html` (script의 `state`, `SM`, `buildSections`, `taskRow`, `stepperNodes`, `mgrRows/empRows`, `adminUsers/adminGroups`, `reviewVariant`, `reviewTasksArr`, `reviewComm`, `aiMetrics`, `onPickRejectTemplate`)

본 문서의 모든 enum 값/라벨/관계는 디자인 파일의 `SM`(상태 메타) 라벨과 `buildSections`/`writeMode` 분기를 그대로 반영했다. enum 이름·컬럼명·라벨은 다른 문서(01-기능명세서·03-API-화면매핑·04-백엔드-자동화)와 완전히 일치시킨다. 디자인에 없는 합리적 보강은 `[보강]`, 불명확 지점은 `[확인필요]`로 표기했다. 정성 지표(효율성/연속성/연관성) AI 산출·표시는 **v1 deferred(범위 외)**.

용어/상태 라벨 정렬(4문서 공통):
- **report_status**(보고서 상태축): `not_written`(미작성)/`writing`(작성중)/`submitted`(제출완료)/`pending_review`(검수대기)/`rejected`(반려)/`resubmitted`(재제출)/`approved`(승인)/`vacation`(휴가)
- **review_status**(검수 상태축): `not_requested`(검수전)/`pending`(검수대기)/`approved`(승인)/`rejected`(반려)/`resubmitted`(재제출)/`exempt`(검수면제) — 디자인 `mgrRows`/`empRows`의 "상태"/"검수" 2컬럼 분리에 대응(§2.3.1·§5.9 참조)
- **section_kind**: `plan`/`morning`/`afternoon`/`night` · **section_status**: `planned`/`writing`/`closed`/`rework`/`not_written`/`exempt` · **is_locked**: 잠금/편집 boolean
- **task_status**: `planned`(계획)/`in_progress`(진행중)/`done`(완결)/`hold`(지연) + 파생 `due_soon`(지연임박, 계산값)

전제(공통):
- 모든 타임스탬프는 `timestamptz`로 저장하고 애플리케이션 레이어에서 `Asia/Seoul`로 변환·판단한다. 보고서의 "날짜"는 KST 영업일 기준의 `date` 컬럼으로 별도 보관한다. `[보강]`
- 모든 테이블 PK는 `bigint GENERATED ALWAYS AS IDENTITY`(이하 `id`)를 기본으로 한다. 외부 노출용 토큰/링크는 별도 `uuid`/문자열 컬럼을 둔다.
- 생성/수정 추적용 `created_at timestamptz NOT NULL DEFAULT now()`, `updated_at timestamptz NOT NULL DEFAULT now()`를 공통으로 둔다(트리거로 `updated_at` 갱신). `[보강]`
- 소프트 삭제가 필요한 마스터(users/groups)는 `deleted_at timestamptz NULL`을 둔다. `[보강]`

## 1) ER 개요

### 1.1 엔티티 목록

| 영역 | 엔티티 | 핵심 역할 |
|---|---|---|
| 조직 | `users`, `groups` | 사용자(역할 1개·그룹 1개), 그룹(그룹장 1명) |
| 인증 | `auth_otps`, `sessions` | 4자리 OTP 로그인, 세션 |
| 보고서 | `daily_reports` | (사용자, 날짜)당 1건. 하루 누적 갱신 |
| 시간대 | `report_sections` | 계획/오전/오후/야간 블록, 잠금/편집 상태 |
| 업무 | `tasks`, `task_attachments`, `task_links` | 업무·첨부(파일/URL)·연속성(이전·이월) |
| 커뮤 | `communications`, `communication_attachments` | 커뮤니케이션 로그·첨부 |
| 코멘트/휴가 | `daily_comments`, `vacations` | 일일 코멘트(1건), 휴가 처리 |
| 검수 | `reviews`, `review_events`, `reject_targets` | 승인/반려, 이력 타임라인, 반려 지목 시간대 |
| 자동화 | `notifications`(이메일 로그), `report_links` | 발송 스케줄/리마인더 로그, 일일 누적 토큰 링크 a |
| 예약(v1 deferred) | `qualitative_metrics` | 효율성/연속성/연관성 — **v1 미산출, 영역 예약만** |

### 1.2 관계 요약 (텍스트 다이어그램)

```
groups ──< users                       (group_id, 사용자는 그룹 1개에 소속)
groups.leader_id ──> users.id          (그룹 1개 = 그룹장 1명; 그룹장 변경 시 검수 권한 이동)

users ──< daily_reports                (작성자 owner_id)
users(=그룹장) ──< reviews              (reviewer_id)

daily_reports 1 ──< report_sections    (계획/오전/오후/야간; 보고서당 최대 4개)
daily_reports 1 ──1 vacations          (휴가일 때만 1건)  ※ partial
daily_reports 1 ──1 daily_comments     (보고서당 1개, 최대 500자)
daily_reports 1 ──< communications     (보고서당 커뮤 로그 N건)
daily_reports 1 ──< reviews            (재제출로 검수 N회 가능, 최신 1건이 현재 상태)
daily_reports 1 ──< review_events      (제출→반려→재제출→승인 타임라인)
daily_reports 1 ──1 qualitative_metrics(예약, v1 deferred)  ※ partial

report_sections 1 ──< tasks            (업무는 한 시간대에 속함)
report_sections 1 ──< reject_targets   (반려 지목: 전체/오전/오후/야간)

tasks 1 ──< task_attachments           (file/url 통합 테이블, 복수)
tasks 1 ──< task_links (next)          (prev_task_id / carryover_source_task_id 자기참조 연속성)

communications 1 ──< communication_attachments

reviews 1 ──< reject_targets           (반려일 때 지목 시간대 N개)
reviews 1 ──< review_events            (해당 검수 회차가 발생시킨 이벤트)

users 1 ──< auth_otps                  (로그인 OTP 발급 이력)
users 1 ──< sessions
daily_reports 1 ──< report_links       (링크 a = 일일 단위 누적 토큰)
daily_reports 1 ──< notifications      (해당 보고서에 대한 발송/리마인더 로그)
```

핵심 불변식:
- 사용자 1명 = **역할 1개**(`users.role`) + **소속 그룹 1개**(`users.group_id`).
- 그룹 1개 = **그룹장 1명**(`groups.leader_id`). 그룹장도 직원처럼 자기 보고서를 작성한다.
- 검수 권한은 "그룹장 ↔ 그룹"으로 파생된다. **별도 권한 테이블 없이** `reviews.reviewer_id`가 작성자 그룹의 현재 `leader_id`인지로 검증한다. → 그룹장 변경 시 권한이 자동 이동.

## 2) ENUM 타입 정의

디자인 `SM` 라벨(완결/진행중/지연/지연임박/검수대기/반려/승인/휴가/미작성/계획/작성중/제출완료/재제출/마감완료/재작성/면제)을 도메인별 enum으로 합리적으로 분해했다.

> **상태 2축 분리(중요)**: 디자인 `mgrRows`/`empRows` 테이블은 **"상태"(report)** 컬럼과 **"검수"(review)** 컬럼을 **별도**로 둔다(예: `sub='제출완료'` + `rev='검수대기'`). 따라서 보고서 상태(`report_status`, §2.3: 미작성/작성중/제출완료/휴가 등)와 검수 상태(`review_status`, §2.3.1: 검수대기/승인/반려/재제출/검수면제)를 **두 개의 enum으로 분리**한다. 03-API 응답(`status` + `review_status`)과 정합한다.

### 2.1 `user_role` — 역할 (3-tier)

| enum 값 | 한글 라벨 | 비고 |
|---|---|---|
| `employee` | 직원 | 자기 보고서 작성/제출 |
| `group_leader` | 그룹장 | 자기 그룹 검수 + 직원처럼 작성 |
| `admin` | 관리자 | 사용자/그룹 관리 (검수 권한과 별개) |

### 2.2 `user_status` — 계정 상태 `[보강]` (디자인 adminUsers `active` 표현)

| enum 값 | 한글 라벨 |
|---|---|
| `active` | 활성 |
| `inactive` | 비활성 |

### 2.3 `report_status` — 보고서 상태(작성/제출 축)

| enum 값 | 한글 라벨 | 디자인 근거 |
|---|---|---|
| `not_written` | 미작성 | SM 미작성, stepperNodes |
| `writing` | 작성중 | SM 작성중, empRows |
| `submitted` | 제출완료 | SM 제출완료, empRows/mgrRows("상태" 컬럼) |
| `pending_review` | 검수대기 | SM 검수대기, review |
| `rejected` | 반려 | SM 반려 |
| `resubmitted` | 재제출 | SM 재제출 (반려 후 다시 제출) |
| `approved` | 승인 | SM 승인 |
| `vacation` | 휴가 | SM 휴가 |

> `[보강]` "제출완료"와 "검수대기"는 디자인상 거의 동의어로 쓰이나(제출 즉시 검수 큐 진입), 상태 추적을 위해 분리 보관한다. 표시 정책은 화면 문서에서 정의.
> **2축 분리 운영**: `report_status`는 디자인 테이블의 **"상태"** 컬럼축이다. 검수 결과(승인/반려/재제출)는 `review_status`(§2.3.1)로 별도 관리하되, 검수 진행 중에는 `report_status`도 동기 전이(`pending_review`/`rejected`/`resubmitted`/`approved`)시켜 단일 보고서 상태 질의를 단순화한다. 즉 같은 의미를 두 축이 공유한다(중복은 의도된 비정규화). 디자인 `mgrRows`의 두 컬럼은 §5.9의 매핑으로 산출한다.

### 2.3.1 `review_status` — 검수 상태(검수 축) `[보강: 디자인 2컬럼 분리 반영]`

디자인 `mgrRows`/`empRows`의 **"검수"** 컬럼(검수대기/승인/반려/재제출/—)에 대응한다. `daily_reports.review_status`로 보관하고, 검수 라우팅·목록 검수 배지의 단일 소스로 쓴다.

| enum 값 | 한글 라벨 | 디자인 근거 |
|---|---|---|
| `not_requested` | 검수전 | mgrRows/empRows 검수 컬럼 "—"(미제출이라 검수 미요청) `[보강]` |
| `pending` | 검수대기 | SM 검수대기, mgrRows `rev='검수대기'` |
| `approved` | 승인 | SM 승인, "[승인됨] … 이정민 팀장" |
| `rejected` | 반려 | SM 반려, 반려 모달 |
| `resubmitted` | 재제출 | SM 재제출 |
| `exempt` | 검수면제 | 검수 대상 아님(예: 미작성·작성중) `[보강]` |

> 휴가 보고서도 검수 대상이므로 `review_status`는 `vacation`과 무관하게 `pending→approved/rejected`로 진행한다(§5.6).

### 2.4 `section_kind` — 시간대 종류

| enum 값 | 한글 라벨 | 시각 기준 |
|---|---|---|
| `plan` | 계획 | 08:30 |
| `morning` | 오전 | ~11:50 마감 |
| `afternoon` | 오후 | ~17:50 마감 |
| `night` | 야간 | 선택, 종료 예상시각 |

> stepperNodes의 노드 순서(`plan→morning→afternoon→night`)와 일치.

### 2.5 `section_status` — 시간대(블록) 작성 상태

| enum 값 | 한글 라벨 | 디자인 근거 |
|---|---|---|
| `planned` | 계획 | buildSections '계획' (초기 미작성과 구분되는 계획 단계) |
| `writing` | 작성중 | buildSections '작성중' (editable 섹션) |
| `closed` | 마감완료 | buildSections '마감완료' (locked 섹션) |
| `rework` | 재작성 | rejected 모드의 '재작성/재작성 필요' (지목된 시간대) |
| `not_written` | 미작성 | stepperNodes '미작성' |
| `exempt` | 면제 | SM `면제`(icon `–`) — **라벨만 존재, `buildSections` 미사용** `[보강]` |

> 잠금(locked)/편집가능(editable)은 `report_sections.is_locked`(boolean)로 표현하고, `section_status`는 의미상 상태를 담는다. `buildSections`에서 `locked⇒마감완료/표시접힘`, `editable⇒작성중`으로 매핑됨.
> **`exempt` 근거 명확화**: SM에는 `면제` 라벨이 존재하나 `buildSections`/`stepperNodes` 어디에서도 실제 렌더에 쓰이지 않는다(휴가는 `stepperNodes`에서 4개 노드를 모두 `휴가`로 처리). 따라서 `exempt`는 디자인 코드 근거 없는 `[보강]`이며, "야간 미해당/해당없음" 등 **시간대 행이 존재하되 작성 의무가 없는 경우** 표현용으로만 도입한다(§5.5: 야간 '없음'은 행 미생성이 원칙).

### 2.6 `task_status` — 업무 상태 (디자인 SM enum)

| enum 값 | 한글 라벨 | SM 색/아이콘 |
|---|---|---|
| `planned` | 계획 | 회색 `·` |
| `in_progress` | 진행중 | #2563EB `◔` |
| `done` | 완결 | #1F9254 `✓` |
| `hold` | 지연 | #DC2626 `!` (hold_reason 사용) |

> 파생 상태 **지연임박**(`due_soon`, #D97706 `◷`)은 마감 임박 **계산값**이므로 컬럼/enum에 저장하지 않고 애플리케이션에서 산출한다.
> **보고서 단위 지연 요약(`delay`)**: 디자인 `mgrRows`/`empRows`의 `delay` 컬럼은 업무 단위가 아니라 **보고서 단위 지연 요약값**으로 `'정상'/'지연임박'/'지연'` 3종이다(03-API §1.9 응답 `delay` 필드와 동일). 산출 규칙 `[보강]`: 해당 보고서 업무 중 **마감시각 임박(미완)** 이 있으면 `지연임박`, **마감 초과 미완(`task_status='hold'` 등)** 이 있으면 `지연`, 그 외 `정상`. 이 값도 저장하지 않고 조회 시 계산한다.

### 2.9 `reject_template` — 반려 자주 쓰는 사유 템플릿

| enum 값 | 한글 라벨 | 디자인 근거(`rejectTemplates`) |
|---|---|---|
| `schedule_missing` | 일정 누락 | '일정 누락' |
| `insufficient_basis` | 근거 불충분 | '근거 불충분' |
| `close_error` | 완결 처리 오류 | '완결 처리 오류' |
| `comm_missing` | 커뮤니케이션 기록 누락 | '커뮤니케이션 기록 누락' |
| `need_detail` | 내용 구체화 필요 | '내용 구체화 필요' |
| `custom` | 직접 입력 | 템플릿 없이 코멘트만 작성 `[보강]` |

> `[보강: 템플릿=코멘트 프리필]` 디자인 `onPickRejectTemplate`은 선택한 템플릿 라벨을 **코멘트 textarea에 그대로 채울 뿐**(`rejectComment = dataset.tpl`), 별도 enum 컬럼으로 저장하지 않는다. 따라서 `reviews.template` 컬럼(§3.14)으로의 분리 저장과 `custom` 값은 모두 **분석·집계용 보강**이다. 미사용 시 `reviews.template`은 NULL로 두고 코멘트(`reviews.comment`)만 저장해도 무방하다.

### 2.10 `reject_scope` — 반려 지목 대상 시간대

| enum 값 | 한글 라벨 | 디자인 근거(반려 모달 대상 지목) |
|---|---|---|
| `all` | 전체 시간대 | '전체 시간대' |
| `morning` | 오전 | '오전' |

- **CHECK**: `role <> 'group_leader' OR group_id IS NOT NULL` (그룹장은 소속 그룹 필수) `[보강]`
- **인덱스**: `idx_users_group (group_id)`, `idx_users_role (role)`

- **`department`/`group` 관계**: 디자인 `adminUsers`는 부서명과 그룹명을 사실상 동일 축으로 쓴다(개발팀/마케팅팀 등이 그룹이자 부서, `groupOptions`에 '운영'도 그룹으로 포함). 별도 `department` 컬럼은 표시 중복 대비 `[보강]`이며 근거가 약함.

| 컬럼 | 타입 | NULL | 기본값 | 설명 |

| `report_id` | bigint | N | | 소속 보고서 |

| `planned_at` | timestamptz | Y | | 발송/마감 기준 시각(08:30/11:50/17:50/야간) `[보강]` |

- **UNIQUE**: `UNIQUE (report_id, kind)` ← 보고서당 시간대 종류 1개
- **인덱스**: `idx_sections_report (report_id)`
- **블록 수 vs 행 수 `[확인필요]`**: 디자인 `buildSections`는 같은 시간대라도 `writeMode`에 따라 **표시 블록 수**가 다르다. 예: `morningClose`는 오전을 `mp`(오전 계획, locked) + `mc`(오전 마감, editable) **2블록**으로 렌더하고, `afternoonClose`부터는 `오전 (계획·마감)` **1블록**으로 병합한다. 그러나 본 모델은 `UNIQUE(report_id, kind)`로 **kind당 1행**이다. 따라서 "오전 계획/오전 마감"은 **같은 `morning` section 1행의 2단계 뷰(계획 입력값 + 마감 입력값을 같은 행에 누적)**로 보는 것을 정본으로 한다. 별도 2행이 필요하다면 `UNIQUE`를 `(report_id, kind, phase)`로 확장해야 하므로, 이 모델링 결정은 01 §2.4와 함께 `[확인필요]`로 남긴다.
- **섹션 표시명은 writeMode 종속**: 동일 `kind`라도 표시명이 모드별로 다르다(`morningClose`: '오전 계획'/'오전 마감' → `afternoonClose`+: '오전 (계획·마감)', `nightClose`: '야간 계획·마감'). 표시명은 UI 파생값이므로 컬럼화하지 않는다. `[보강]`

- **목적**: 발송 스케줄/리마인더/반려 안내/OTP 메일 로그. 멱등성·중복발송 방지.

| 컬럼 | 타입 | NULL | 기본값 | 설명 |
|---|---|---|---|---|

| `dedup_key` | text | N | | 멱등키(중복발송 방지). 정본 포맷 = `kind|user_id|report_date|section_kind|reminder_seq` |

| `error` | text | Y | | 실패 사유 |
| `reminder_seq` | smallint | Y | | 리마인더 회차(5분 단위) |
| `created_at` | timestamptz | N | now() | |

- **PK**: `id`
- **FK**: `user_id → users(id) ON DELETE CASCADE`, `report_id → daily_reports(id) ON DELETE SET NULL`
- **UNIQUE**: `UNIQUE (dedup_key)` ← 멱등/중복발송 방지의 핵심.
- **인덱스**: `idx_notif_user_date (user_id, report_date)`, `idx_notif_kind_status (kind, status)`, `idx_notif_scheduled (scheduled_at) WHERE status = 'queued'`
- **멱등키 정본(3문서 통일)**: `dedup_key = kind|user_id|report_date|section_kind|reminder_seq`. 이 포맷을 **정본**으로 삼아 03-API §1.11·04-백엔드 §3.3가 동일하게 사용한다(04-백엔드의 `stage` 세그먼트는 실존 enum인 `section_kind`로 치환). 안내(`plan_link` 등)는 `reminder_seq`가 NULL, 리마인더는 `section_kind`+`reminder_seq`로 회차 구분.
  - 예(안내): `plan_link|42|2026-06-18|plan|`
  - 예(리마인더): `reminder|42|2026-06-18|morning|3`
- **반려 멱등키 `[보강]`**: 반려 안내(`reject_notice`)는 검수 회차당 1통이므로 `kind|user_id|report_date|section_kind|reminder_seq` 패턴(예: `reject_notice|owner_id|report_date||`)으로 충분하다. 만약 04-백엔드처럼 **검수 회차(review)당 1통**을 키로 보장하려면 `notifications`에 `review_id bigint REFERENCES reviews(id)` 컬럼을 추가하고 키에 포함해야 한다 — 현 모델에는 `review_id`/`stage` 컬럼이 **없으므로** v1은 위 정본 포맷을 사용한다. `[확인필요: reject_notice 회차 단위 멱등 필요 시 review_id 컬럼 보강]`

## 4) 전체 DDL

```sql
-- =========================================================
-- Seeding 데이터 모델 · PostgreSQL DDL
-- 타임존: 저장은 timestamptz(UTC), 판정은 앱에서 Asia/Seoul
-- =========================================================

CREATE EXTENSION IF NOT EXISTS citext;
CREATE EXTENSION IF NOT EXISTS pgcrypto;  -- gen_random_uuid()

-- ---------- ENUM TYPES ----------
CREATE TYPE user_role               AS ENUM ('employee','group_leader','admin');
CREATE TYPE user_status             AS ENUM ('active','inactive');
CREATE TYPE report_status           AS ENUM ('not_written','writing','submitted','pending_review','rejected','resubmitted','approved','vacation');
CREATE TYPE review_status           AS ENUM ('not_requested','pending','approved','rejected','resubmitted','exempt');
CREATE TYPE section_kind            AS ENUM ('plan','morning','afternoon','night');
CREATE TYPE section_status          AS ENUM ('planned','writing','closed','rework','not_written','exempt');
CREATE TYPE task_status             AS ENUM ('planned','in_progress','done','hold');
CREATE TYPE review_action           AS ENUM ('approve','reject');
CREATE TYPE review_event_type       AS ENUM ('submitted','rejected','resubmitted','approved');
CREATE TYPE reject_template         AS ENUM ('schedule_missing','insufficient_basis','close_error','comm_missing','need_detail','custom');
CREATE TYPE reject_scope            AS ENUM ('all','morning','afternoon','night');
CREATE TYPE vacation_type           AS ENUM ('annual','half_day','sick','official','etc');
CREATE TYPE comm_type               AS ENUM ('call','email','meeting','kakao','verbal','etc');
CREATE TYPE attachment_kind         AS ENUM ('file','url');
CREATE TYPE notification_kind       AS ENUM ('plan_link','morning_close_link','afternoon_close_link','night_link','reminder','reject_notice','login_otp');
CREATE TYPE notification_status     AS ENUM ('queued','sent','failed','skipped');
CREATE TYPE qualitative_metric_kind AS ENUM ('efficiency','continuity','relevance');

-- ---------- updated_at trigger ----------
CREATE OR REPLACE FUNCTION set_updated_at() RETURNS trigger AS $$
BEGIN NEW.updated_at = now(); RETURN NEW; END;
$$ LANGUAGE plpgsql;

-- ---------- groups (선언, leader FK는 users 생성 후 부착) ----------
CREATE TABLE groups (
  id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  name        text NOT NULL,
  leader_id   bigint,                       -- → users(id), 아래에서 FK 부착
  created_at  timestamptz NOT NULL DEFAULT now(),
  updated_at  timestamptz NOT NULL DEFAULT now(),
  deleted_at  timestamptz
);
CREATE UNIQUE INDEX uq_groups_name ON groups (name) WHERE deleted_at IS NULL;

-- ---------- users ----------
CREATE TABLE users (
  id              bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  login_id        citext NOT NULL,
  name            text   NOT NULL,
  email           citext NOT NULL,
  department      text,
  position_title  text,
  role            user_role   NOT NULL DEFAULT 'employee',
  group_id        bigint      REFERENCES groups(id) ON DELETE SET NULL,
  status          user_status NOT NULL DEFAULT 'active',
  avatar_url      text,
  created_at      timestamptz NOT NULL DEFAULT now(),
  updated_at      timestamptz NOT NULL DEFAULT now(),
  deleted_at      timestamptz,
  CONSTRAINT ck_users_leader_group CHECK (role <> 'group_leader' OR group_id IS NOT NULL)
);
CREATE UNIQUE INDEX uq_users_login_id ON users (login_id) WHERE deleted_at IS NULL;
CREATE UNIQUE INDEX uq_users_email    ON users (email)    WHERE deleted_at IS NULL;
CREATE INDEX idx_users_group ON users (group_id);
CREATE INDEX idx_users_role  ON users (role);

-- groups.leader_id FK (상호참조 → DEFERRABLE)
ALTER TABLE groups
  ADD CONSTRAINT fk_groups_leader
  FOREIGN KEY (leader_id) REFERENCES users(id) ON DELETE SET NULL
  DEFERRABLE INITIALLY DEFERRED;
CREATE INDEX idx_groups_leader ON groups (leader_id);

-- ---------- auth_otps ----------
CREATE TABLE auth_otps (
  id            bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  user_id       bigint NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  code_hash     text   NOT NULL,
  purpose       text   NOT NULL DEFAULT 'login',
  report_date   date,
  expires_at    timestamptz NOT NULL,
  consumed_at   timestamptz,
  attempt_count smallint NOT NULL DEFAULT 0 CHECK (attempt_count >= 0),
  created_at    timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX idx_otp_user_active ON auth_otps (user_id, expires_at) WHERE consumed_at IS NULL;

-- ---------- sessions ----------
CREATE TABLE sessions (
  id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  user_id     bigint NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  token_hash  text   NOT NULL UNIQUE,
  ip          inet,
  user_agent  text,
  expires_at  timestamptz NOT NULL,
  revoked_at  timestamptz,
  created_at  timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX idx_sessions_user    ON sessions (user_id);
CREATE INDEX idx_sessions_expires ON sessions (expires_at);

-- ---------- daily_reports ----------
CREATE TABLE daily_reports (
  id                    bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
```

## 5) 설계 노트 (도메인 → 데이터 표현)

### 5.1 누적 보고서 (하루 1건, append/edit)
- `daily_reports`에 `UNIQUE(owner_id, report_date)`로 (사용자, 날짜)당 1건을 강제. 하루 동안 링크 a(`report_links.token`, 보고서당 1개)로 같은 행을 반복 갱신.
- `write_mode`로 현재 작성 단계(morningPlan→morningClose→afternoonClose→nightClose→view, 그리고 vacation/rejected)를 보존해 재진입 시 동일 화면을 복원. `updated_at`이 "저장됨 · 오후 5:52" 표시의 근거.
- `report_links.expires_at`는 KST 영업일 경계로 만료 → 링크는 일일 단위 토큰.

### 5.2 시간대 잠금(locked)/편집가능(editable)
- `report_sections.is_locked`(boolean)가 잠금/편집을 표현. `buildSections`에서 `locked⇒마감완료(접힘), editable⇒작성중(펼침)`으로 매핑. `section_status`는 의미 상태(`closed`=마감완료, `writing`=작성중, `planned`=계획, `rework`=재작성).
- `closed_at`은 강제 마감/개별 마감 시각. 강제 마감은 해당 section의 미완 tasks를 일괄 `status='done'`으로 전환하는 트랜잭션으로 처리.
- 잠긴 시간대 펼쳐보기(`openLocked`)는 UI 상태이므로 DB 저장 대상 아님.

### 5.3 반려 지목 + 부분 재작성
- 반려는 `reviews(action='reject', comment 필수)`로 기록하고, 지목 시간대를 `reject_targets(scope=all/morning/afternoon/night)`에 1행 이상으로 저장.
- 직원의 rejected 모드: `reject_targets`에 지목된 시간대의 section만 `is_locked=false`/`section_status='rework'`로 열고, 나머지는 잠금 유지 → "지목된 시간대만 재작성" 강제.
- 재작성 후 재제출 시 `daily_reports.status='resubmitted'`, `review_events(event_type='resubmitted')` 추가. 타임라인은 `review_events`가 제출→반려→재제출→승인 순서로 누적.

### 5.4 검수 권한 (그룹장 ↔ 그룹)
- 별도 권한 테이블 없이 `reviews.reviewer_id`가 작성자(`daily_reports.owner_id`)의 그룹(`daily_reports.group_id`)에 대한 현재 `groups.leader_id`인지로 검증. → 그룹장 변경 시 권한이 자동 이동(도메인 계약).
- 보고서에 작성 시점 `group_id` 스냅샷을 두어, 추후 그룹 이동이 있어도 검수 라우팅·이력 추적이 어긋나지 않게 함. `[보강]`
- **그룹장 본인 보고서 검수 `[확인필요]`**: 검수자 = 작성자 그룹의 현재 `leader_id`이므로, 그룹의 **유일 그룹장이 자기 보고서를 작성**하면 자기 자신이 검수자가 되어 자기 검수가 발생한다. 관리자는 검수 권한이 없으므로(01 §1.1 도메인 계약) 그대로 두면 "검수 불가" 모순이 생긴다. 정책 권장(미확정): 그룹장 본인 보고서는 **self-review 면제로 자동 승인**(`review_status='exempt'` 또는 `approved`)하거나, **상위 검수자(예외적으로 admin 위임)에게 라우팅**한다. 채택 시 03-API `requireReviewer`의 `owner_id=me.id` 처리와 01 §1.1의 "관리자 검수 권한 없음" 문구가 그 예외를 함께 반영해야 한다.

### 5.5 야간 분기
- `daily_reports.night_branch`(boolean): NULL=미선택, false=없음, true=있음.
  - **API 페이로드 매핑**: 03-API/01-기능명세는 야간을 `branch:'yes'|'no'|null` 문자열(디자인 핸들러 `onNightYes/onNightNo` 인용)로 표기하나, **저장은 `night_branch boolean`(true/false/NULL)**이다. 서버에서 `'yes'→true`, `'no'→false`, `null→NULL`로 매핑한다.
- 있음(`true`)이면 `night_reason` 필수(CHECK `ck_report_night_reason`)이고, 승인자(그룹장)에게도 검수 화면에 표시(reviewNightReason). `night_expected_end_at`이 "종료 10분 전 재발송" 트리거(`notifications.kind='night_link'`)의 기준 시각.
- 없음(`false`)이면 **`night` section 행을 생성하지 않는다**(일일 코멘트+커뮤니케이션 작성 후 최종 제출). `section_status='exempt'`는 야간없음에 쓰지 않으며, **휴가 등 별도 사유로 행이 이미 존재할 때만** 사용한다. 이 규칙(미생성 원칙 / exempt는 행 존재 시에만)을 01 §2.4·§4.5, 03-API §1.2/§1.7과 동일 문장으로 적용한다.

### 5.6 휴가
- 그 날짜 보고서를 휴가로 처리: `vacations(report_id, type, comment)` 1건 + `daily_reports.status='vacation'` 동기화.
- 휴가 보고서도 검수 대상 → `reviews`/`review_events`가 동일하게 적용(휴가 변형 검수 화면).
- stepperNodes의 휴가 모드는 모든 노드를 휴가로 표시하지만, 이는 표시 로직이고 DB는 보고서 상태 + 휴가 1건으로 충분.

### 5.7 연속성 (이전·다음 / 이월 / 반복)
- `task_links`로 표현: `prev_task_id`(이전 업무 직접 참조), `carryover_source_task_id`("어제 미완료 불러오기" 원본), `link_type`(continue/carryover/recurring).
- 프로젝트명 자동완성/최근 진행 업무는 `tasks.project` 인덱스로 조회(RECENT/PROJECTS 동작 대응). 별도 마스터 테이블 없이 과거 tasks에서 distinct/최근순으로 산출. `[보강]`

### 5.8 정성 지표 (v1 deferred)
- `qualitative_metrics`는 효율성/연속성/연관성을 위한 **예약 테이블**. 디자인의 AI 분석 패널은 "이번 버전 미개발 · 영역 예약" 상태로, **v1에서는 산출/표시 로직 범위 외**. 디자인 `reviewVariant`의 `analyzing`("분석 중") 변형 및 `reviewShowAI`/`reviewAnalyzing` 파생 플래그도 **v1 미사용**(AI 미개발과 함께 deferred). enum/변형 자체는 디자인에 존재하므로 누락 처리하지 않는다.
- 컬럼(`score/grade/comment/computed_at`)은 향후 산출 결과를 담기 위한 자리만 확보하며 v1에서는 NULL 유지. 검수는 AI 없이 진행 가능.

### 5.9 보고서 상태 2축(report_status ↔ review_status) 매핑
디자인 `mgrRows`/`empRows`는 **"상태"(report)** 와 **"검수"(review)** 를 별도 컬럼으로 표시한다. 두 enum(§2.3, §2.3.1)은 아래처럼 동기 전이한다(검수 진행 중에는 `report_status`도 동의어로 함께 갱신해 단일 질의를 단순화 — 의도된 비정규화).

| 시점/이벤트 | `report_status` | `review_status` | mgrRows "상태" / "검수" 표시 |
|---|---|---|---|
| 발송 전/미작성 | `not_written` | `not_requested` | 미작성 / — |
| 작성 중(임시저장) | `writing` | `exempt`(검수 대상 아님) | 작성중 / — |
| 최종 제출 직후 | `submitted` → `pending_review` | `pending` | 제출완료 / 검수대기 |
| 그룹장 승인 | `approved` | `approved` | 승인 / 승인 |
| 그룹장 반려 | `rejected` | `rejected` | 반려 / 반려 |
| 반려 후 재제출 | `resubmitted` → `pending_review` | `resubmitted`(검수 큐 재진입) | 재제출 / 검수대기 |
| 휴가 제출 | `vacation` | `pending`(휴가도 검수 대상) | 휴가 / 검수대기 |

- 목록 검수 배지·검수 큐(`reviews.queue`)는 `review_status IN ('pending','resubmitted')`를 본다.
- 03-API 응답의 `status`(=report_status)와 `review_status`가 본 2축과 1:1 정합한다.
