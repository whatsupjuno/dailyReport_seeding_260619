핵심 어휘 정렬(디자인 `mgrRows`/`empRows`/`SM`은 **보고서 상태**와 **검수 상태**를 별도 두 축으로 둔다 — 아래 §2.0 참조):
- **report_status**(보고서, 작성 진행 축 — 디자인 행의 "상태"열): `not_written`(미작성)/`writing`(작성중)/`submitted`(제출완료)/`vacation`(휴가). + 검수 결과가 보고서에 되먹임되는 파생 상태 `pending_review`(검수대기)/`rejected`(반려)/`resubmitted`(재제출)/`approved`(승인)는 검수 축과 공유.
- **review_status**(검수 결과, 디자인 행의 "검수"열): `pending_review`(검수대기)/`approved`(승인)/`rejected`(반려)/`resubmitted`(재제출)/없음(미제출이면 `—`). 데이터 모델은 v1에서 이 두 축을 `daily_reports.status` 단일 enum + 최신 `reviews`로 표현한다(데이터모델 §2.3).
- **writeMode**(작성 화면 7모드 + 부가): `morningPlan`/`morningClose`/`afternoonClose`/`nightClose`/`view`(+`vacation`/`rejected`)
- **section_kind**: `plan`/`morning`/`afternoon`/`night` · **section_status**: `planned`/`writing`/`closed`/`rework`/`not_written`/`exempt` · **is_locked**: 잠금/편집 boolean
- **task_status**: `planned`(계획)/`in_progress`(진행중)/`done`(완결)/`hold`(지연) + 파생 `due_soon`(지연임박, 계산값)

## 1) 역할·권한 매트릭스

3-tier 역할(`user_role`): `employee`(직원) · `group_leader`(그룹장) · `admin`(관리자). 사용자 1명 = 역할 1개 + 소속 그룹 1개(관리자도 그룹을 가질 수 있다 — 디자인 `adminUsers`의 관리자 박소라 그룹='운영'). 검수 권한은 "그룹장 ↔ 그룹"으로 파생되며 별도 권한 테이블 없이 `reviews.reviewer_id == 작성자 그룹의 현재 groups.leader_id`로 검증한다(그룹장 변경 시 권한 자동 이동).

### 1.1 화면 접근 (LNB: 작성/목록/검수/관리)

| 화면(LNB) | 직원 | 그룹장 | 관리자 | 비고 |
|---|---|---|---|---|
| 작성(write) | ✅ 자기 보고서 | ✅ 자기 보고서 | ⚠️ `[확인필요]` | 그룹장도 직원처럼 자기 보고서 작성. 관리자 본인 작성 여부는 디자인 미확정 → `[확인필요]` |
| 목록(list) · 직원 뷰 | ✅ 내 보고서 | ✅ 내 보고서 | — | `listRole='employee'`: "내 보고서" |

## 2) 일일 보고서 생애주기 상태머신

세 층위가 맞물린다: ① 보고서 상태(`report_status`) ② 작성 화면 모드(`writeMode`, 7모드) ③ 시간대 잠금/편집(`report_sections.is_locked` + `section_status`). 모든 판정은 KST 영업일/시각 기준.

### 2.0 두 축(보고서 상태 / 검수 상태) 분리 — 디자인 행 구조

디자인 목록 테이블은 헤더가 **"상태"**(report)와 **"검수"**(review) 두 컬럼이고, `mgrRows`/`empRows`도 `sub`(보고서 상태)와 `rev`(검수 상태)를 **별도 값**으로 보유한다:

- **보고서 상태(sub)**: `미작성`/`작성중`/`제출완료`/`휴가` (작성 진행 축)
- **검수 상태(rev)**: `검수대기`/`승인`/`반려`/`재제출`, 미제출이면 `—` (검수 결과 축)
- 예: 김지원 = `제출완료`(sub) + `검수대기`(rev), 정유나 = `제출완료`(sub) + `승인`(rev), 최민호 = `재제출`(sub) + `검수대기`(rev).

데이터 모델은 v1에서 이 두 축을 **단일 `daily_reports.status` enum + 최신 `reviews` 1건**으로 표현한다(데이터모델 §2.3): `제출완료`는 `submitted`(검수 대기 큐 진입 시 `pending_review`로 추적), 검수 결과는 `reviews.action`/`review_events`에서 파생. 화면 렌더 시 한 보고서가 "상태=제출완료, 검수=검수대기"처럼 두 배지로 동시 표기될 수 있다(아래 §3.4 헤더 복수 배지). 검수 배지가 없는 행(미작성/작성중/휴가-미검수)은 `rev='—'`.

### 2.1 report_status 전이도

| 현재 상태 | 이벤트(트리거) | 다음 상태 | 비고 |
|---|---|---|---|
| `not_written` | 계획 링크 발송(08:30) | `not_written` | 메일만, 상태 변화 없음 |
| `not_written` | 작성 시작(첫 입력/임시저장) | `writing` | `daily_reports.updated_at` 갱신, "저장됨" 표시 |
| `not_written`/`writing` | 휴가로 전환 후 휴가 제출 | `vacation` | `vacations` 1건 생성 + status 동기화 |
| `writing` | 계획 제출(morningPlan) | `writing` | 계획만 확정, 제출완료 아님 `[보강]` |
| `writing` | 오전 마감(morningClose) | `writing` | 오전 section `is_locked=true`, 보고서는 아직 미제출 |
| `writing` | 야간 계획 저장(nightClose·야간있음, 1차) | `writing` | 1차 저장: `night_expected_end_at` 확정, 상태 유지. 야간 종료 후 2차 최종 제출로 이어짐(§4.5) |
| `writing` | 최종 제출(afternoonClose / 야간없음 nightClose / 야간있음 2차) | `submitted` → `pending_review` | `first_submitted_at`/`last_submitted_at` 기록, 검수 큐 진입 |
| `submitted` | 검수 큐 진입(제출 즉시) | `pending_review` | 디자인상 제출완료(sub) + 검수대기(rev). 추적 위해 분리 보관(데이터모델 §2.3) |
| `pending_review` | 그룹장 승인(`onApprove`) | `approved` | `approved_at` 기록, `reviews(action='approve')` |
| `pending_review` | 그룹장 반려(`onSubmitReject`) | `rejected` | `reviews(action='reject')` + `reject_targets` |
| `rejected` | 지목 시간대 재작성 후 재제출 | `resubmitted` → `pending_review` | `review_events(resubmitted)`, `last_submitted_at` 갱신 |
| `resubmitted` | 그룹장 승인/반려 | `approved`/`rejected` | 회차 누적(`reviews.round`) |
| `approved` | (종료) | — | 당일 확정. 읽기 전용 |
| `vacation` | 그룹장 승인/반려 | `approved`/`rejected` | 휴가 보고서도 검수 대상 |

검수 이력 타임라인(`review_events`): `submitted → rejected → resubmitted → approved` 순으로 누적(디자인 검수 이력: 제출 11:48 → 반려 13:05·이정민 → 재제출 17:54 → 검수 대기 중).

### 2.2 writeMode(7모드) 전이도

`writeMode`는 작성 화면이 현재 어느 단계를 그리는지 결정(`daily_reports.write_mode` 보존, 재진입 복원용). 시각 진행 + 사용자 액션으로 전이.

| writeMode | 진입 조건 | 표시 핵심 | primary 버튼(`writePrimary`) | 다음 모드(이벤트) |
|---|---|---|---|---|
| `morningPlan` | 08:30 계획 단계, 오전 미마감 | 오전 계획 섹션(`editable`) 1개 | `계획 제출` | 오전 마감 시 → `morningClose` |
| `morningClose` | 오전 마감 단계(~11:50) | 오전계획(locked)+오전마감(editable)+오후계획(editable) 3블록 | `오전 마감하기` | 오전 잠금 후 → `afternoonClose` |
| `afternoonClose` | 오후 마감 단계(~17:50) | 오전(locked)+오후마감(editable) + 커뮤·코멘트 | `최종 제출` | 제출→`view` / (도메인상 야간 분기 시 →`nightClose`, 단 디자인 야간 토글은 nightClose 전용 — §4.5 `[확인필요]`) |
| `nightClose` | 야간 단계(선택) | 오전·오후(locked) + 야간 토글(`showNightToggle`) + (있음)야간섹션 | 야간있음 `야간 계획 저장` / 야간없음 `최종 제출` | 야간 종료 후 2차 최종 제출 → `view` |
| `view` | 최종 제출 후 | 전 섹션 locked, 읽기 전용 | `제출 완료`(회색, 비활성) | (검수 결과 대기) |
| `vacation` | "휴가로 전환" 클릭 | 휴가 유형+코멘트 폼 | `휴가로 제출`(회색) | 제출 시 status=`vacation` |
| `rejected` | 반려 후 "재작성하러 가기" | 지목 시간대만 `editable`(`재작성 필요`), 나머지 locked | `재제출하기` | 재제출 → `view`(status=`resubmitted`) |

> 야간 '있음'/'없음' 분기 값(`nightBranch='yes'`/`'no'`)은 디자인 핸들러(`onNightYes`/`onNightNo`) 표기이며, **저장은 `daily_reports.night_branch boolean`**(yes→true / no→false / 미선택→NULL)으로 매핑한다.
> 모드 전환 트리거(디자인 핸들러): `onGoVacation`→`vacation`, `onExitVacation`→`morningClose`, `goWriteRejected`→(`screen='write'`,`writeMode='rejected'`), 야간 토글 `onNightYes`/`onNightNo`. 데모용 `onVariant`는 `morningClose`/`afternoonClose`/`nightClose` 간 미리보기 전환(`afternoonClose` 선택 시 `nightBranch=null` 리셋).

### 2.3 스테퍼 노드 상태(`stepperNodes`) — writeMode별 매핑

stepper 노드 순서: `plan(계획·08:30) → morning(오전·11:50) → afternoon(오후·17:50) → night(야간·21:30)`. 야간 시각 `21:30`은 디자인 고정 예시값이며 실제는 `night_expected_end_at` 동적. 각 노드 상태와 현재(current) 표시는 모드에 종속.

| writeMode | plan | morning | afternoon | night | current |
|---|---|---|---|---|---|
| `morningPlan` | 계획 | 미작성 | 미작성 | 미작성 | plan |
| `morningClose` | 완결 | 미작성 | 미작성 | 미작성 | morning |
| `afternoonClose` | 완결 | 완결 | 미작성 | 미작성 | afternoon |
| `nightClose` | 완결 | 완결 | 완결 | 미작성 | night |
| `view` | 완결 | 완결 | 완결 | 미작성 | (없음) |
| `rejected` | 완결 | 완결 | 반려 | 미작성 | afternoon |
| `vacation` | 휴가 | 휴가 | 휴가 | 휴가 | (없음) |

글리프: 완결=✓, 지연=!, 반려=↩, 휴가=/. 연결선은 직전 노드 완결이면 녹색(`#1F9254`).

### 2.4 시간대(section) 잠금/편집 전이

`buildSections` 매핑: **locked(잠금)** ⇒ `is_locked=true`, `collapsed`(접힘), `section_status='closed'`(마감완료) · **editable(편집)** ⇒ `is_locked=false`, `expanded`(펼침), `section_status∈{writing,planned,rework}`. 좌측 보더 강조(`#3B5BDB`)는 editable 섹션.

| 이벤트 | section 전이 | 비고 |
|---|---|---|
| 시간대 발송 시각 도래(계획/오전/오후/야간) | `not_written/planned → writing` (`is_locked=false`) | 편집 가능, 카드 펼침 |
| 오전 마감하기 | 오전 `writing → closed` (`is_locked=true`) | 미완 업무는 강제 마감 처리 후 잠금 |
| 오후 마감(최종 제출) | 오후 `writing → closed` | 전 섹션 잠금 → `view` |
| `강제 마감`(`onForceClose`) | 해당 section 미완 tasks 일괄 `done`, section `closed` | §4.3 `[확인필요]`. 디자인은 `data-titles`로 업무만 일괄 완결 |
| `업무 펼쳐 보기 ▾`/`접기 ▴`(`onToggleLocked`) | UI만 펼침/접힘 | `openLocked` (UI 상태, DB 비저장) |
| 반려 + 시간대 지목(`reject_targets`) | 지목 section `closed → rework`(`is_locked=false`), 나머지 유지 | rejected 모드: 지목된 곳만 편집 허용 |
| 야간 없음(`night_branch=false`) | 야간 section **미생성** | exempt는 야간 미생성 표현이 아님 — 아래 주석 참조 |

> **섹션 표시명은 writeMode에 종속**(`buildSections`): 오전은 `morningClose`에서 `오전 계획`(locked, `mp`) + `오전 마감`(editable, `mc`) **2블록**으로, `afternoonClose`부터는 `오전 (계획·마감)`(locked, `m`) **1블록**으로 병합 렌더. 오후는 `오후 계획`(`ap`, morningClose) → `오후 마감`(`ac`)으로, 야간은 `야간 계획·마감`(`nc`). **[확인필요]**: morningClose의 오전 계획+오전 마감 2블록이 `report_sections`에서 같은 `morning` kind의 2단계 뷰인지 별도 2행인지 — 데이터 모델 `UNIQUE(report_id, kind)`(kind당 1행)와 정합되도록 "1행 + 단계별 뷰"로 보는 것을 권장(데이터모델 §3.6 [확인필요]와 연계).

> **`exempt`의 용도 `[보강]`**: SM에 라벨 `면제`(아이콘 `–`)가 존재하나 `buildSections`/`stepperNodes` 렌더에는 직접 쓰이지 않는다. `exempt`는 **휴가 등 별도 사유로 시간대 행이 존재하되 작성 면제일 때만** 사용한다. **야간 '없음'은 `night` section을 생성하지 않으므로 exempt를 쓰지 않는다**(이전의 "미생성 또는 exempt" 양자택일 표현은 제거).

### 3.1 로그인 (SCREEN 1 · login)

- **주요 컴포넌트**: 로고/슬로건, 안내 배너(`loginBanner`), 에러 알림(`loginError`), 아이디 입력(`#login-id`), OTP 4칸(`otpDigits`, inputmode=numeric, maxlength=1, 자동 포커스 이동·붙여넣기 분해·백스페이스 역이동), 로그인 버튼(`onLoginSubmit`), 문의 링크, 데모 진입("로그인 없이 둘러보기" `onDemoEnter` — 디자인 검토용, 실서비스 비노출 `[보강]`).
- **상태/표시**:
  - 안내 배너: "로그인하면 **6월 18일 업무 보고서**로 바로 이동합니다." (`auth_otps.report_date` 기반 당일 보고서로 이동) `[보강]`
  - 버튼 활성(`ready`): **아이디 입력(`idVal.trim().length>0`) + OTP 4자리 완성(`otp.join('').length===4`)** 일 때만 파란색(`#3B5BDB`), 미완 시 비활성 회색(`#E2E5EB`, cursor not-allowed).
- **입력/검증**(`onLoginSubmit` 근거):
  - 존재하지 않는 아이디 → "존재하지 않는 아이디입니다. 다시 확인해 주세요."
  - OTP 불일치(4자리 입력했으나 틀림) → "인증번호가 일치하지 않습니다. 다시 입력해 주세요." + OTP 초기화·첫 칸 포커스
  - 미입력/4자리 미만 → 버튼 비활성으로 클라이언트에서 차단(서버 호출 안 함). 안내 "아이디와 인증번호 4자리를 모두 입력해 주세요."
  - OTP 검증 정책 `[보강]`: `auth_otps.code_hash` 대조, `expires_at` 만료/`consumed_at` 사용 여부 확인, `attempt_count` 증가(N회 초과 시 잠금).
- **에러 표시(정밀)**: 에러 시 빨강 알림. **아이디 입력 보더 빨강(`#DC2626`)은 "아이디가 `unknown.user`이거나 빈 아이디"일 때만**(`idBorder` 조건). OTP만 불일치한 경우엔 아이디 보더는 빨강이 아니다.
- **케이스**: 로딩(버튼 라벨 "로그인 중…", `loginLoading`), 에러(빨강 알림 + 위 조건의 보더 빨강), 성공(세션 생성 후 당일 작성 화면 이동).
- **API**:
  - `POST /api/auth/otp/request` — 요청 `{ loginId }` → OTP 발급·메일 발송(`notification_kind='login_otp'`), 응답 `{ ok, expiresInSec }`. OTP 만료 예시값은 03-API/04-백엔드와 통일(권장 5분) `[확인필요: 5분 vs 30분]`.
  - `POST /api/auth/login` — 요청 `{ loginId, code }` → 응답 `{ session, redirect:{ screen:'write', reportDate } }` 또는 `{ error }`.
  - `POST /api/auth/logout` — 세션 무효화(`sessions.revoked_at`).

### 3.2 작성 (SCREEN 2 · write) — 7모드 공통/모드별

**공통 레이아웃**: 페이지 헤더(날짜 + "저장됨 · 오후 5:52" `aria-live`), 알림 배너(`writeBanner`), 진행 스테퍼(§2.3), "지금 할 일" 헤더 카드(`writeHeader.title/sub` + 마감 임박 `writeDeadline`), 시간대 섹션 스택(`sections`), 커뮤니케이션/일일 코멘트(해당 모드), sticky 액션바(임시저장 + primary).

**섹션 카드 구성요소**:
- editable(펼침): 잠금 아이콘 없음, 시간대명·시간범위, `강제 마감` 버튼, 상태 배지(`section_status`), 업무 목록, `＋ 업무 추가` + `↻ 어제 미완료 불러오기` + `반복 업무`(이 세 버튼은 **모든 editable 섹션**에서 노출 — morningPlan 포함).
- locked(접힘): 잠금 아이콘, 시간대명, 접힘 요약줄(`summary` 예 "완결 2 · 지연 1 — …") + 토글 버튼(`onToggleLocked`, 라벨 `업무 펼쳐 보기 ▾` ↔ 펼친 상태 `접기 ▴`).

**업무 행 구성요소**(`taskRow`): 체크원(완결=녹색✓ / 지연=빨강! / 그 외 빈원), 프로젝트 칩(있을 때), 업무명, 상태 배지(`task_status`), 상세(`계획 120분 / 실제 150분`), 지연 사유(hold), `마감` 버튼(editable·미완결), ⋯ 메뉴.

**업무 추가 폼**(`addOpen`): 프로젝트명(선택, 칩 `PROJECTS` + 입력 시 "최근 진행한 업무" 자동완성 `RECENT`), 업무명(필수), 예정 시작 시각(`TIME_OPTS`, 30분 단위), 소요 시간(`DUR_OPTS`, 30분 단위), 첨부파일+코멘트(복수), URL+코멘트(복수), 취소/추가. **[보강]**: 디자인 데모에서 "추가" 버튼은 `onCancelAdd`(폼 닫기만)에 연결돼 있으나, 실서비스는 `POST .../tasks`로 저장한다.

|---|---|---|---|---|
| `morningPlan` | 오전 계획(editable, 업무=계획 상태) | 배너 "오전 보고 미작성·11:50까지". 마감 임박 문구 없음(`writeDeadline` 미표시) | 업무명 필수, 시간 30분 단위 | `계획 제출` |

  - `POST /api/reports/:id/submit` → 모드별 제출(`morningPlan`/`morningClose`/`final`; 야간있음은 1차 저장→2차 final 2단계); 최종 제출 시 `pending_review`
  - `POST /api/reports/:id/vacation` `{ type, comment }` → `vacation`

### 3.3 목록 (SCREEN 3 · list) — 관리자(팀) 뷰 / 직원 뷰

`listRole`로 두 변형. 제목/부제: 관리자="팀 보고 현황 / 오늘 팀의 제출·검수 상태…", 직원="내 보고서 / 내가 작성한 일일 업무 보고서…".

**관리자(팀) 뷰**:
- **통계 4카드**(`listStats`): 오늘 제출(14/18명·진행률 78% 바), 미제출(4명, 빨강), 지연(3건, ! 빨강), 검수 대기(6건, ⧗ `#B7860B`).
- **탭**(`listTabsArr` mgr): 전체(18)/미제출(4)/지연(3)/검수대기(6)/반려(1)/승인(4). 카운트 칩 포함.
- **필터**: 기간(오늘/최근 7일/최근 30일/이번 달), 부서(전체 직원/개발팀/마케팅팀), 검색("이름·업무 내용으로 검색").
- **테이블 행**(`mgrRows`, **두 축 분리** §2.0): 직원(아바타·이름·부서), 날짜, **상태**(`report_status` 배지 = `sub`: 미작성/작성중/제출완료/재제출/반려/휴가), **검수**(`review_status` 배지 = `rev`: 검수대기/승인/반려, 없으면 —), 완결율(바+`9/10`), 지연(보고서 단위 요약값 정상/지연임박◷/지연!), 제출시각, 액션(`검수`=파란 버튼 / `보기`). 미작성·지연 행은 좌측 라인 강조(`rowLine`).
- **지연 요약값**(`delay`): 보고서 단위로 정상/지연임박/지연 3값. 산출 규칙 `[보강]` — 시간대 마감시각 임박+미완 = `지연임박`(`due_soon`), 마감 초과 미완 = `지연`(`hold`/마감 미완).
- **그룹장 범위**: 자기 그룹 구성원만. 관리자는 스코프 강제 없이 전체(선택적 그룹 필터) `[보강]`.

**직원 뷰**:
- 반려 배너(`showEmpRejectBanner`): "반려된 보고서가 1건 있어요. 사유를 확인하고 재작성해 주세요."
- 통계 카드 없음. 탭(`listTabsArr` emp): 전체(6)/작성중(1)/제출완료(2)/반려(1)/승인(2).
- 테이블 행(`empRows`): 날짜(요일), **상태** 배지(sub), **검수** 배지(rev, 없으면 —), 완결율, 지연, 제출시각, › (상세 이동). 휴가일은 상태=휴가, 검수=—, 완결율/제출=—.
- **케이스**: 빈 상태(탭 결과 0건 → "표시할 보고서가 없습니다" `[보강]`), 로딩(스켈레톤 `[보강]`), 페이지네이션("총 18건", 이전/숫자/다음), 모바일은 카드형.
- **API**: `GET /api/reports?view=manager|employee&status=&period=&dept=&q=&page=` → `{ rows(status+review_status 분리), stats?, total, page }`. manager 뷰는 그룹장(자기 그룹 강제 필터)/관리자(전체, 선택 group 필터)만.

### 3.4 검수 (SCREEN 4 · review) — 2컬럼

`reviewVariant`: `pending`/`approved`/`rejected`/`resubmitted`/`vacation`/`employee`(직원 읽기) + `analyzing`(AI 분석 중 변형 — **v1 미사용**, 아래 주석). 파생 플래그 `reviewShowAI`(= `rv !== 'analyzing' && rv !== 'vacation'`)/`reviewAnalyzing`(= `rv === 'analyzing'`).

> **`analyzing` 변형 `[v1 deferred]`**: 디자인 `reviewVariant` enum에 존재하나 AI 분석 패널이 "분석 중"일 때의 변형이다. AI 정성 지표가 v1 미개발이므로 **v1에서는 사용하지 않는 변형**으로 둔다(enum 자체는 디자인에 존재하므로 누락 처리하지 않음).

- **상단 글로벌 바**: "← 목록으로", 검수 큐 위치(`reviewQueuePos`: "검수 대기 8건 중 3번째") + 이전◀/다음▶(직원 읽기 변형 `employee`는 큐 숨김 `reviewQueuePos=null`), 검수자명.
- **상태 배너**(`reviewStatusBanner`): approved="[승인됨] … 이정민 팀장", rejected="[반려됨] 그룹장 코멘트 · …", resubmitted="[재제출] 17:54 · 변경된 섹션을 확인…".
- **보고서 헤더 카드**: 작성자(아바타·이름·부서·직급), 날짜, **복수 상태 배지 병렬**(보고서 상태 배지 + 파생 `↻ 재제출`/`! 지연` 배지 동시 표시 가능 — 예 `⧗ 검수대기` + `↻ 재제출` + `! 지연`), 메타(`reviewMetaText`: 최초제출·반려·재제출 시각), 완결 요약("완결 7 · 지연 2 · 미완 1 · 전체 10").
- **좌 본문**(2컬럼 좌측):
  - 휴가 변형(`reviewIsVacation`): "휴가일입니다 (연차)" + "휴가 보고서도 관리자 확인 필요…".
  - 일반: 야간 사유 박스(`reviewNightReason`, "작성자 제출" 태그), 오전/오후 섹션(읽기 전용 업무 목록, 지연 행 빨강 라인), 커뮤니케이션 기록(`reviewComm`), 일일 코멘트.
- **우 사이드**(sticky): **AI 분석 패널**(보라, "이번 버전 미개발 · 영역 예약", 효율성/연속성/연관성 자리만, 값 "—") — **v1 deferred**. **휴가/`analyzing` 변형에서는 AI 패널 미표시**(`reviewShowAI=false`). 검수 이력 타임라인(제출→반려→재제출→검수 대기 중). 직원 읽기 변형(`isEmployeeRead`): "그룹장 반려 코멘트" + `재작성하러 가기 →`(`goWriteRejected`).
- **검수 액션바**(`showReviewActionbar`, 직원 읽기 제외): 완결 요약 + `반려`(빨강 보더)/`승인`(녹색).
- **반려 모달**(`rejectModalOpen`):
  - 자주 쓰는 사유(`rejectTemplates`): 일정 누락/근거 불충분/완결 처리 오류/커뮤니케이션 기록 누락/내용 구체화 필요 (`reject_template` enum; 직접 입력=`custom`). **[보강]**: 디자인은 템플릿 칩 클릭(`onPickRejectTemplate`) 시 라벨을 **코멘트 textarea에 그대로 프리필**하며 별도 컬럼 저장이 아님. `reviews.template` 분리 저장·`custom` 값은 보강.
  - 대상 지목 select: 전체 시간대/오전/오후/야간 (`reject_scope` → `reject_targets`). **[보강]**: 디자인은 **단일 select(1개 지목)**, 데이터/`scopes[]`의 복수 허용은 확장 보강.
  - 그룹장 코멘트(필수). 빈 코멘트면 제출 차단(`onSubmitReject`: `if (!comment.trim()) return`), 제출 버튼(`반려하고 코멘트 전달`) 비활성 회색(`rejectSubmitBg`).
- **케이스**: 빈 큐(검수 대기 0 → "검수할 보고서가 없습니다" `[보강]`), 로딩, 권한 없음(타 그룹 보고서 403), 모달 검증 실패(코멘트 미입력).
- **API**:
  - `GET /api/reviews/queue?position=` → 큐 목록/현재 위치
  - `GET /api/reviews/report/:id` → 검수용 보고서 상세(야간 사유·이력·커뮤·복수 배지 조합 포함)
  - `POST /api/reviews/:reportId/approve` `{ comment? }` → `reviews(action='approve')`, status=`approved`
  - `POST /api/reviews/:reportId/reject` `{ comment(필수), template?, scopes:['all'|'morning'|'afternoon'|'night'] }` → `reviews(action='reject')` + `reject_targets` + `review_events(rejected)` + 반려 안내 메일(`reject_notice`)
  - 서버 검증: 요청자 == 작성자 그룹 현재 그룹장, 대상 status==`pending_review`.

### 3.5 관리 (SCREEN 5 · admin) — 사용자 / 그룹

`adminTab`: `users`/`groups`. 관리자 전용.

**사용자 관리**(`isAdminUsers`):
- 헤더("총 N명"), 검색("이름·아이디로 검색"), `＋ 사용자 추가`.
- 추가 폼(`addUserOpen`): 이름(필수)/아이디(필수)/소속 그룹(select `groupOptions`: 개발팀/마케팅팀/디자인팀/영업팀/운영)/역할(select `roleOptions`: 직원/그룹장/관리자). 관리자도 그룹 지정 가능.
  - **[확인필요: 이메일 입력 경로]**: 디자인 추가 폼에는 **이메일 입력란이 없다**(4개 필드만). 그러나 OTP/안내 메일 발송에 이메일은 **필수**다. 이메일(및 부서/직급) 입력 경로를 v1에서 어떻게 확보할지 확정 필요 — 추가 폼 확장 또는 별도 수정 화면.
- 테이블(`adminUsers`): 이름(아바타), 아이디(=`login_id` 표시), 소속 그룹, 역할 배지(관리자/그룹장/직원 색 구분), 상태(활성✓/비활성·), `수정`.
- 검증 `[보강]`: 아이디·이메일 미삭제 범위 유니크(`uq_users_login_id`/`uq_users_email`), 역할=그룹장이면 소속 그룹 필수(`ck_users_leader_group`).

**그룹/그룹장 관리**(`isAdminGroups`):
- 안내 배너: "그룹장은 자기 그룹 구성원의 보고서만 승인·반려. 그룹장 변경 시 검수 권한도 함께 이동."
- 헤더("총 N개 그룹"), `＋ 그룹 추가`(그룹명 필수 + 그룹장 select).
- 그룹 카드(`adminGroups`): 그룹명, 구성원 수, 그룹장(아바타·"승인 권한" 태그), 구성원 칩 목록, `그룹장 변경`/`구성원 관리`.
  - **[보강]**: 디자인에서 `그룹장 변경`/`구성원 관리` 버튼은 핸들러가 없는 데드 버튼(변경 모달/플로우 미구현). `PUT .../leader`·`memberIds` 동기화 동작은 보강이다.
- 그룹장 변경 시: `groups.leader_id` 갱신 → 검수 권한 자동 이동(별도 권한 테이블 없음).
- **케이스**: 빈 그룹(구성원 0), 그룹장 미지정(`leader_id` NULL 일시 허용 `[확인필요]`), 중복 그룹명 차단(`uq_groups_name`).
- **API**:
  - `GET /api/admin/users?q=`, `POST /api/admin/users` `{ name, loginId, email, groupId, role }`, `PATCH /api/admin/users/:id`
  - `GET /api/admin/groups`, `POST /api/admin/groups` `{ name, leaderId }`, `PATCH /api/admin/groups/:id` `{ name?, leaderId?, memberIds? }`

## 4) 비즈니스 규칙

### 4.1 누적 보고서 · 링크 a
- (사용자, 날짜)당 1건(`uq_report_owner_date`). 하루 동안 동일 이메일 링크 a(`report_links.token`, 보고서당 1개)로 같은 행을 append/edit. 토큰은 KST 영업일 경계로 만료(`expires_at`). 로그인/링크 진입 시 당일 보고서로 이동.

### 4.2 시간대 마감/잠금
- 시간대는 발송 시각 도래로 `editable`(`is_locked=false`)이 되고, 마감 액션으로 `closed`(`is_locked=true`, 접힘 요약). 잠긴 시간대는 `업무 펼쳐 보기 ▾`/`접기 ▴`로 UI에서만 펼침/접힘(`openLocked`, DB 비저장).
- 오전 마감(morningClose) → 오전 잠금 + 오후 계획 진입. 오후 마감(afternoonClose 최종 제출) → 전 섹션 잠금 + `view`.

### 4.3 개별 마감 / 강제 마감
- 개별 마감(`마감`, `onCloseTask`): 단일 업무를 `done`으로 전환(`closed_at`). 디테일 없으면 "개별 마감 완료" 표시.
- 강제 마감(`강제 마감`, `onForceClose`): 한 시간대의 미완 업무 전체를 일괄 `done`으로 전환. **[확인필요]**: 디자인 `onForceClose`는 `data-titles` 기반으로 **업무 일괄 완결만** 수행하고 섹션을 잠그지(`is_locked`) 않는다. 문서·API는 강제마감을 "일괄 완결 + 섹션 잠금" 마감 트랜잭션에 포함시켰으므로, 섹션 잠금 책임을 강제마감(`force-close`)이 갖는지 별도 `마감하기`(`sections/:id/close`)가 갖는지 — 두 액션의 책임 경계를 확정해야 한다.

### 4.4 휴가
- "휴가로 전환"(morningClose/afternoonClose 프롬프트 `showVacationPrompt`, `onGoVacation`) → `vacation` 모드. 유형(연차/반차/병가/공가/기타, `vacation_type`) 필수 + 코멘트. 제출 시 `vacations` 1건 + `daily_reports.status='vacation'` 동기화.
- 휴가 보고서도 그룹장 검수 대상(승인/반려). "← 업무 작성으로"(`onExitVacation`)로 `morningClose` 복귀.

### 4.5 야간 분기 (사유·종료시각 · 2단계 제출)
- 야간 분기 토글(`showNightToggle`, 디자인상 **nightClose 전용** — §3.2 `[확인필요]`)에서 "야간 업무 있음/없음" 선택. API 페이로드 `branch:'yes'|'no'|null`은 서버에서 `daily_reports.night_branch boolean`(true/false/NULL)으로 매핑한다.
  - **있음**: 야간 사유 필수(`night_reason`, 승인자에게도 표시), 종료 예상시각(`night_expected_end_at`) 지정 → 종료 **10분 전 재발송**(`notification_kind='night_link'`). **2단계 제출** — 1차 `야간 계획 저장`(상태 `writing` 유지, `night_expected_end_at` 확정) → 야간 종료 후 2차 `최종 제출`(→`pending_review`).
  - **없음**: 야간 `night` section을 **생성하지 않고**(exempt 미사용), 일일 코멘트+커뮤니케이션 작성 후 `최종 제출`.
- 사유는 검수 화면 야간 박스("작성자 제출")로 노출.

### 4.6 반려 시간대 지목 후 재작성 범위
- 반려 시 `reject_targets`에 지목(전체/오전/오후/야간) 저장. 직원 rejected 모드: 지목 section만 `is_locked=false`/`section_status='rework'`("재작성 필요")로 열고 나머지는 잠금 유지 → "지목된 시간대만 재작성" 강제(액션바: "반려된 시간대만 편집할 수 있어요"). 미지목 시간대 수정 시 `409 NOT_REWORK_TARGET`.
- 재작성 후 `재제출하기` → `resubmitted` → `pending_review`, `review_events(resubmitted)` 추가.

### 4.7 임시저장 vs 제출
- **임시저장**: `status` 'writing' 유지, 검수 큐 미진입. "저장됨 · 시각" 표시(`updated_at`).
- **제출**: 모드별 의미 분리 — 계획 제출/오전 마감/야간있음 1차 저장은 보고서 상태를 제출완료로 만들지 않음(`writing` 유지). **최종 제출**(afternoonClose, 야간없음 nightClose, 또는 야간있음 2차)만 `submitted→pending_review`로 검수 큐 진입.

### 4.8 연속성 (어제 미완료 / 반복)
- `↻ 어제 미완료 불러오기` → 전일 미완 업무를 당일로 이월(`task_links.carryover_source_task_id`, `link_type='carryover'`). `반복 업무` → `link_type='recurring'`. 두 버튼은 모든 editable 섹션(morningPlan 포함)에서 노출.
- 프로젝트명 입력 시 최근 진행 업무 자동완성(`RECENT`/`PROJECTS`) → 과거 `tasks.project`에서 최근순 산출(별도 마스터 없음). 이전 업무 직접 참조는 `prev_task_id`(`link_type='continue'`).

### 5.1 발송 스케줄·리마인더 (상세는 백엔드 문서)
모든 발송은 KST·영업일(평일) 기준, NCP Outbound Mailer. 멱등/중복방지는 `notifications.dedup_key`(정본 포맷: `kind|user_id|report_date|reminder_seq` — 데이터모델 §3.18, 세 문서 통일).

|---|---|---|
| 계획 링크 | `plan_link` | 평일 08:30 |
| 오전마감 링크 | `morning_close_link` | 평일 11:50 |
| 오후마감 링크 | `afternoon_close_link` | 평일 17:50 |
