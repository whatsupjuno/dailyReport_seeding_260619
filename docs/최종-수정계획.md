## 0. 한줄 요지 + 현재앱 ↔ 디자인 핵심 격차

**한줄 요지**: 현재 앱은 5화면이 동작하지만 **(a) #4 라이프사이클이 "순차 섹션 모델(plan→morning→afternoon→night, 7모드)"** 이라 브리프의 "단일 오늘할일 + 완료시각 자동분류"와 근본적으로 다르고, **(b) 댓글·휴직·업무단위 반려가 없으며**, **(c) 스타일이 부분 불일치**(커뮤니케이션 배지 원형화, 셸 모바일 0폭 위험)이다. 데이터/배포는 기존계획 `0005~0009`·`P0~P8`을 그대로 잇고, 본 계획은 그 위에 디자인 토큰·문구·노출 규칙과 충돌 2건 결정을 확정한다.

| 영역 | 현재 앱 | 디자인(브리프 §) | 핵심 격차 |
|---|---|---|---|
| 작성 #4 | 섹션 순차 카드 + `computeWriteMode` 7모드 | 단일 "오늘 할 일" + 오전/오후/야간 버킷(§4.2) | **모델 전면 교체** |
| 라이프사이클 | 단일 제출(7모드) | **계획 제출 + 최종 제출 2단계 + 개별검수 상시**(확정 #4) | **C2** |
| 야간 | 토글/사유 이미 인라인 존재(섹션종속) | 토글 vs 시각≥20:00(§4.2 vs 확정) | **C1 + 재배치** |
| 검수 #3 | 보고서/시간대 반려만 | 업무 행단위 반려 + 부분반려 회신(§4.4) | **신규 테이블·전이 분리** |
| 댓글 #1 | 없음 | 작성·검수 공통 우측 드로어(§5) | **신규 전체** |
| 휴가 #2 | 유형 셀렉트만 | 휴직 + 필수/선택 사유 + 10,000자(§4.2) | **검증·읽기카드 누락** |
| 스타일 | 배지 9999 원형 존재, 셸 인라인 display로 @media 무효 | 22px/라운드6 사각칩, `display:block`(§4.2/§8) | **토큰·반응형 정합** |

## 1. 결정 필요 3건 (착수 전 확정 필수) [검증 B3]

> 세 결정은 데이터모델·상태전이·검수 게이트·휴가 전환에 직접 파급하므로 먼저 못박는다. 결정 후 모든 스키마·코드가 이를 따른다. (C1·C2는 충돌 해소, B3는 신규 정책 결정.)

### ⚠ C1 — 야간 분류 규칙: 독립 토글(night flag) vs 마감시각 ≥20:00

| 근거 | 규칙 |
|---|---|
| 브리프 §4.2(L97)·§6 task 스키마 | "야간 업무가 있나요? 없음/있음" **독립 토글**(`night?: boolean`), "오전·오후와 무관". 디자인 L416/420. 🌙배지(L345)는 업무 단위 플래그. |
| 확정 #4 | 마감 시각 **≥20:00 → 야간**(시각 컷오프). |
| 기존계획 `[A]/[B]` | `is_night`은 0009 컬럼, 분류는 `completed_at`(KST) 시 <12 오전 / ≥12 오후(2분기, 야간 미반영). |

**결정 제안 (D-C1) — 하이브리드: `tasks.is_night` 플래그가 SoT, 시각 ≥20:00은 디폴트 제안값.**
- **데이터 SoT = 업무 단위 `tasks.is_night boolean`**(디자인·브리프 충실, 0009 컬럼 그대로). `classify()`는 `is_night===true`인 업무를 **무조건 야간 바구니**로(오전/오후와 독립) — 브리프 §6 "night는 별도 바구니" 일치.
- **확정 #4의 ≥20:00은 버리지 않고 `closeTask`의 `is_night` 기본 제안값으로 흡수**: 마감 시 클라가 `isNight` 미전달이면 `completed_at`(KST) 시 ≥20 → `is_night=true` 디폴트, 사용자가 토글을 끄면 그 값을 존중(서버는 클라 전달값 우선).
- **🌙 야간 배지·토글의 사유 textarea는 유지**: 토글 "있음" 시 야간 사유 필수(브리프 L97/L427), 골드 콜아웃 "이 사유는 승인자(그룹장)에게도 표시됩니다".
- **검수는 영향 없음**: 검수 야간 카드(§4.4)는 작성 산출물(boolean + 사유)을 재계산 없이 표시.
- **근거**: 디자인은 픽셀·동작 충실(hifi, 브리프 §1)이 최우선 → "별도 바구니=플래그"가 SoT여야 목업과 일치. ≥20:00은 "야간 깜빡 누락" UX 보정 디폴트로 살림 → 두 명세 모두 충족.
- **스키마 영향: 추가 0건**(0009의 `is_night` 컬럼으로 충분). 시각 로직은 DB가 아니라 `classify.ts` + `closeTask`에만.

### ⚠ C2 — 제출 라이프사이클: 단일 제출 vs 계획제출+최종제출 2단계 & 개별검수 상시

| 근거 | 모델 |
|---|---|
| 브리프 §4.2 | `writeMode = work/view/rejected/vacation`, 제출 1회→view. 단일 제출 뉘앙스(단 "계획 제출/최종 제출" 단어 존재). |
| 브리프 §4.4 | 행 단위 반려 상시 + 승인 시 부분반려 확인 모달. |
| 확정 #4 | **계획 제출(1차, 잠금 아님) + 최종 제출(1회)**. 개별검수는 **계획 제출 직후부터 상시**, 전체 승인/반려는 **최종 제출 후**. |
| 기존계획 `[C]/[I]` | "신규 report status enum 미추가" / "행 반려는 status 불변, 회신만 전이". |

**결정 제안 (D-C2) — 확정 #4 채택: status에 `계획제출` 1개 추가 + 2단계 제출, writeMode는 4종 유지.**

| 단계 | report status | writeMode | 작성자 권한 | 검수자 권한 |
|---|---|---|---|---|
| 아침 작성 | `작성중` | `work` | 추가·마감·수정·삭제 자유 | 없음 |
| **계획 제출 후** | **`계획제출`(신규)** | `work` | **여전히 자유**(제출=잠금 아님) | **개별 업무 승인/반려 상시** |
| 최종 제출 후 | `검수대기` | `view` | 읽기 전용 | **전체 승인/반려** + 개별 |
| 반려 | `반려` | `rejected` | 반려행만 편집 | (재제출 대기) |
| 휴가 | (`is_vacation`) | `vacation` | 휴가 카드만 | 읽기 |

- **2단계 제출 라벨**: 액션바 `[제출하기]`가 status로 분기 — `작성중→"계획 제출"`, `계획제출→"최종 제출"`, `rejected→"재제출하기"`, `view→"제출 완료"(비활성)`. **라벨 함수는 `model_version`으로 v1(legacy)·v2(2단계) 분리**(§4.4·§5.3, [검증 B4]).
- **계획 제출은 잠금 아님**: `계획제출`에서도 `addTask`/`closeTask`/`updateTask`/`deleteTask` 허용. 잠금 화이트리스트 = `{검수대기, 승인, 제출완료, 재제출}` + 반려 미해소행만.
- **게이트 분리(핵심)**: **행 반려(개별검수) = `계획제출 ∨ 검수대기` 상시**(`assertReviewable`). **전체 승인/반려 = `검수대기`만**(`assertPending` 유지, 기존계획 `[I]`/A-1 정합). → "전체 승인·반려는 최종 제출 후".
- **검수 큐 진입 필터 확장(치명) [검증 B2]**: `계획제출` status는 `submitted_at`이 NULL이라 현재 `reviewQueueForReviewer`(review.ts)·`listReviewQueue`(review.ts)·목록 검수 큐 필터(list.ts)의 `status='검수대기'` 조건에 **걸려 큐에 뜨지 않는다** → 개별검수 상시가 전면 무력화. **세 필터를 모두 `status IN ('계획제출','검수대기')`로 확장**해야 `계획제출` 보고서가 검수 진입 가능. 큐 카운트("검수 대기 N건") 분모도 `IN (...)` 기준으로 재정의. 변경 파일: `src/lib/data/review.ts`·`src/lib/data/list.ts`(아래 §3.2.2/§3.3/§4.3 반영).
- **`rejectTask`(status 불변) ↔ `rejectReport`(`검수대기→반려` 전이) 엄격 분리** — 동일시하면 둘째 행반려가 `NOT_PENDING(409)`으로 실패(기존계획 A-1, 본 영역 최대 버그 위험). 현재 `rejectReport`는 `assertPending` 사용 → **기존 `rejectReport`의 `assertPending` 유지 + 신규 `rejectTask`만 `assertReviewable`로 분리**(E2 정합).
- **1차 제출 표식 [결정 D-C2b]**: `review_event_kind` enum 확장 대신 **`daily_reports.plan_submitted_at timestamptz`(추가형 컬럼, NULL 허용)** 1개로 표현(마이그레이션 경량). 컬럼 미도입 시 [폴백] = `검수대기` 단일 게이트(브리프와 동일, 상시검수 미지원).
- **status.ts 타입·메타 동반 갱신(필수) [검증 B1]**: Postgres enum 추가만으로 부족 — TS `ReportStatus` 유니언과 `STATUS_META`에 `계획제출`이 없으면 `statusMeta('계획제출')`이 fallback('미작성' 회색)으로 깨진다. **`src/lib/domain/status.ts`: `ReportStatus`에 `'계획제출'` 추가 + `STATUS_META['계획제출']` = 진행중 청색 재사용(`#2563EB`/`#E6EEFD`/`#BBD0F7`) 등록**(변경 파일로 명시, §5.1·§4.2).
- **근거**: 확정 #4가 브리프보다 우선. status enum은 `ADD VALUE`만이라 추가형·안전. 브리프 단일 `work` 뉘앙스는 `work`를 두 status(`작성중`/`계획제출`)에 매핑해 흡수 → 디자인 4모드 + 라이프사이클 2단계 동시 충족.
- **기존계획 `[C]` 갱신**: "`계획제출` 1개는 예외 추가"로 수정(아래 §5 충돌해소표).

### ⚠ B3 — `계획제출`에서 근태(휴가) 전환 허용 여부 [신규 결정 · 검증 B3]

| 근거 | 규칙 |
|---|---|
| 현재 코드 | `advanceReport`의 휴가우회 가드(report-mutations.ts)는 `status !== '미작성' && !== '작성중'`이면 `VACATION_NOT_ALLOWED`. |
| 확정 #4 | 계획 제출 후에도 "하루 종일 업무 추가·마감" 허용. |

**문제**: C2로 `계획제출` status가 생기면, "계획 제출 후 근태(휴직 등) 변경"은 status가 이미 `계획제출`이라 **이 가드에 걸려 휴가 전환 불가**. 확정 #4의 "이후에도 종일 작성 허용"과 충돌 가능. 미결정 시 advance가 `VACATION_NOT_ALLOWED(409)`로 사용자 혼란.

**결정 제안 (D-B3) — 허용**: 가드 화이트리스트를 `{미작성, 작성중, 계획제출}`로 확장. 계획 제출 후라도 종일 작성을 허용하는 #4 취지와 정합.
- **허용 시**: advance 휴가우회 가드를 화이트리스트(`미작성/작성중/계획제출`)로 처리, `계획제출`에서 근태변경 버튼 활성.
- **불허 시(대안)**: 근태변경 버튼을 `계획제출` status에서 비활성 처리(가드는 현행 유지).
- 영향: report-mutations.ts 가드 1줄(화이트리스트), ReportEditor 근태변경 버튼 노출 조건, security.spec 회귀.

- **교차 FK·CHECK 재검증 [검증 B5]**: `계획제출` enum 추가는 `tasks`/`task_rejections` FK·CHECK에 무영향(`task_status`와 별개 enum). `tasks_completed_at_chk`는 `(status IN ('완결','지연')) = (completed_at IS NOT NULL)`이라 **`is_night` 미관여** → "예정 야간"(토글 on·미마감)은 `is_night=true && completed_at=NULL`로 허용되되 **그 전제는 `status∈{계획,진행중}`** 일 때만 성립(완결/지연이면 completed_at 필수). 명문화: "야간 미마감 task = `status∈{계획,진행중} ∧ completed_at=NULL`(야간 배지만, todo 바구니); 야간 마감 시 `완결/지연 ∧ completed_at NOT NULL`(C1 is_night과 직교)". `classify.test`에 "is_night=true·status=계획·completed_at=NULL → todo 바구니(야간 배지)" 케이스 추가. 야간 task 완결 처리 시 completed_at 누락하면 CHECK 위반이므로 구현 주의.
